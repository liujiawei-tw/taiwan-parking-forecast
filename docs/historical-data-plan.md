# 停車歷史資料取得與 ML 試驗計畫

查核日期：2026-09-23。來源：[TDX 歷史服務清單](https://tdx.transportdata.tw/data-service/historical)、[停車歷史 API 說明](https://tdx.transportdata.tw/api-service/swagger/historical/bfc9dd07-b597-4851-b20f-82f2c53a0fe1#/OffStreetParkingCityAPI/Historical_ParkingCityAvailability)、[TDX 訂閱收費](https://tdx.transportdata.tw/pricing)。以下是資料取得計畫，尚未用會員帳戶申請或下載檔案。

## 清單與候選資料

TDX 歷史服務的「停車資訊 18」表示 18 種資料集，並非一定要下載 18 份。Sponsor 指定**新北市路邊停車格位動態歷史資料 v1**作為第一個路邊資料探索對象；路外停車場試點也要做，但資料集尚待選定。路邊「單一格位狀態」與路外「停車場剩餘位數」是不同預測目標，兩條流程要分開驗證。

新北市路邊格位歷史 API 範例欄位包含 `ParkingSpotID`、`ParkingSegmentID`、`ServiceStatus`、`SpotStatus`、`DeviceStatus`、`ChargeStatus`、`DataCollectTime`。API 有 CSV／JSONL 格式，日期查詢最多 7 天，`$top` 預設 30。正式分析前仍須確認格位 ID、狀態碼和車種的實際語意。

## 日期與資料切分

2024–2025 年可作為後續季節性研究，但新北市路邊格位單日已有約 300–550 萬筆，首次不能直接申請一週或兩年。Sponsor 提供的 2026 年 8 月每日筆數中，**2026-08-09 最少，仍有 2,938,401 筆**；若網站只允許按整日申請，這是資料量最小的格式試驗候選日，但須先看到 `SizeBytes` 或預估耗點，且保留額度，不直接送出整日申請。若能取得限制筆數的 CSV 樣本，可先做欄位驗證；此類小樣本不能代表整天，也不足以訓練時間序列模型。

一週小樣本只能證明資料管線可行，通常不足以證明模型在不同節日、季節或異常事件下可靠。是否需要兩年資料，應在基準模型與資料漂移檢查後再決定。

## CSV 或 API

- **第一次探索：優先取得 CSV 小樣本。** Jupyter 可直接讀取；便於檢查欄位、時間順序、缺值與體積，且不必先寫下載程式。先檢查 TDX 申請畫面是否可限制資料量，以及是否顯示檔案大小或耗點；對新北市格位資料不可直接假設一整日能負擔。
- **後續可重現擷取：再使用官方歷史 API。** API 要依 TDX 官方 Java 範例實作認證；用固定日期區間、記錄請求與回應，適合排程與資料治理。
- API 說明顯示 `Dates` 單次最多 7 日，`$top` 預設 30，格式有 CSV／JSONL，`Meta=true` 可查 Count 和 SizeBytes。若未確認完整筆數與分頁方式，不能假設一次 API 回應就是整週所有資料。Meta 查詢是否耗點、網站檔案申請的日期上限與點數計法，尚待帳戶頁或官方說明確認。

## 點數風險

歷史服務頁面定價為每 10 次／點加上每 20 MB／點，兩項併計。Sponsor 帳戶目前每月 3 點、使用統計 0。若取 2026-08-09 的 2,938,401 筆，僅用 3 點可對應的 60 MB 計，平均每筆必須不超過約 **20.4 bytes** 才不會單由資料量超額；實際 CSV 有多個 ID、狀態與時間欄位，故完整單日檔案有高度超額風險。TDX 如何計算 CSV 申請檔案的資料量、是否壓縮與是否有額外點數，須以平台顯示的 `SizeBytes`／使用統計確認，不能只憑筆數判定精確費用。

另若透過 API 每次最多 7 天，2024–2025 約 731 天，至少要約 105 個日期區間；即使每區間只需一次請求，僅計次已約 10.5 點，超過每月 3 點，且未算分頁與資料量。因此不以「一次抓完 2024–2025」作為本月計畫。

## 第一份檔案的驗收

取得一個小區間後，先記錄檔名、來源、日期、大小、申請前後點數，再檢查：停車場 ID 數量、每場每天觀測數、`DataCollectTime` 是否連續、車位數是否出現負值或異常跳動，以及能否對應目前 TDX 停車場基本資料。原始檔不要直接提交 Git；只提交不含金鑰或敏感資訊的資料字典、統計摘要與可重現的分析步驟。
