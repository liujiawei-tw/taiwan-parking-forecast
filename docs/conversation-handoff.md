## 產品範圍與已決定的體驗

- 新莊區為 MVP 試點，只做汽車。目的地由 Google 搜尋選取，同一座標同時是 Google Routes ETA 終點與直線 300 公尺停車搜尋圓心；附近實際收錄路邊或路外哪一類，就顯示哪一類。
- 起點支援目前位置及手動選取；出發時間預填當下，也可指定未來時間。只有明確送出／重新規劃才呼叫 Google Routes。直接以當次 Google 交通感知 ETA 作兩類停車預測的共同目標時刻，不自行創造固定抵達時間。原 ETA 已過時提示重新規劃，不再把該次機率顯示為未來預測。
- 路邊主要結果是「抵達時，目的地 300 公尺內至少一個合格汽車格位可停的機率」，次要呈現目前確認有位格位的位置；路外逐停車場顯示抵達時有汽車位的機率。可對有效、新鮮且位置／汽車適用性已核實的格位提供外部地圖路線；本系統不做內建導航、預約或機車。
- 前端採 Vue 3＋Vite，Google Maps JavaScript API 作互動地圖、Place Autocomplete Widget (New) 作搜尋，電腦版以地圖為主並保留路邊區域摘要及「查看全部結果」，手機版地圖在上、清單在下。Google Cloud 專案 `taiwan-parking-forecast` 已建立，三項所需 Google API、帳單連結和預算通知已由 Sponsor 回報完成；帳單規劃由 Sponsor 自行處理，本階段不要再追問。

## 主系統架構與資料邊界

- 後端方向：Java、Spring Boot Web／MVC、Maven、MySQL／JPA、Redis、Docker；Docker 可重現部署是必要交付，未來會移到其他伺服器。多來源先經 adapter 統一欄位、ID、時間、品質狀態，再由主系統 API 提供前端。
- 新莊即時來源由**主系統自行介接新北市官方 API**。`parking-data-collector` 是另一個只供離線 ML 訓練的 Repo，不參與使用者查詢或主系統刷新。該 collector 的資料取得方式目前有問題、資料不完整；依 Sponsor 指示暫緩盤點與模型驗證。TDX 是全臺擴充方向；歷史資料有額度／點數限制。
- MySQL 保存停車目錄、來源對應、已發布的完整快照與可追溯觀測歷史；使用者查詢是第一優先，歷史未來可次要地供離線訓練。Redis 用於短期查詢進度與經驗證的快取，不代替 MySQL 的快照真相或來源用量控制。
- 來源缺頁或無法確認整輪取齊，不發布新快照；少數個別壞值標未知及品質原因。有效 `0`、無資料、過期及未收錄必須分開。系統成功取得後超過 5 分鐘先以過期顯示（試驗門檻）；過期的主要目前可用數為空，舊數值只可附原時間作次要參考，舊「有位」不可作目前導航推薦。來源觀測時間與系統取得時間要分開。
- 建立行程查詢後先回目的地／範圍與可信位置；Google ETA、路邊、路外、兩類預測分階段補齊。進度 GET 只讀，不觸發上游。單一「更新車位」按鈕分別處理路邊與路外，不重算 Google ETA。可見頁面過期時自動嘗試受控刷新，隱藏時暫停；自動與手動同時發生共用後端來源級同一輪擷取，跨使用者／分頁不重複抓。前端重新可見先只讀最新狀態，再判斷是否刷新。

## 目前進度與下一題

- 目前完成的是需求／架構決策和草案文件，**尚未完成主系統程式、端到端展示或模型驗收**。`docs/project-status.html` 是人類可讀的進度視圖；具體狀態以 `docs/current-state.md` 為準。
- **下一個待討論決策：官方來源擷取失敗後如何重試。**上次提案：失敗就停止轉圈並顯示最後成功時間；後端來源級冷卻跨使用者生效。冷卻後最多共用地自動重試一輪，若仍失敗就停止自動重試，容許之後手動更新。此提案**尚未獲 Sponsor 同意**；冷卻秒數及錯誤分類待來源量測，不可把 5 分鐘過期門檻直接當重試間隔。
- 其他重要待決：新北市來源欄位／汽車適用性和實際呼叫成本、快照品質門檻、API 欄位與等待期限、Redis 失效處理、模型可用樣本和回測指標、遠端 Docker 部署環境。詳見 `docs/open-questions.md`。
- 目前工作樹有多份已修改與未追蹤的文件／資料；尚未替使用者建立新 Git 分支或提交。若新分支是獨立 worktree，應確認它包含這些未提交的最新文件，避免只看到舊版 HEAD。
