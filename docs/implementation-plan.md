# 實作順序計畫（Sprint 2 起）

更新日期：2026-09-25。狀態：實作前最後確認；尚未開始 coding。此文件描述開始實作後的建議順序，不代表功能已完成。

## 排序原則

1. 先建立可啟動、可測試、可部署的骨架，再接外部 API。
2. 先讓資料模型、快照發布與狀態降級可運作，再做漂亮畫面。
3. 先用 mock／stub 驗證前後端契約，再接 Google 與政府即時來源。
4. 先做到「目前車位可信顯示」，再接「抵達時預測」。
5. 預測資料不足時明確降級，不用假機率補畫面。

## 建議的第一個可展示版本

第一個可展示版本不要等到 ML 完成。建議目標是：

- 使用固定或手動輸入的新莊目的地座標。
- 後端能查 300 公尺內已收錄路邊與路外位置。
- 能顯示目前車位狀態、資料時間、過期／未知／有效 0。
- API 契約與前端畫面已可跑通。
- 預測區塊先可顯示「預測資料不足」及原因。

這個版本能先證明主系統資料流正確，再逐步加入 Google 搜尋／ETA 與預測。

## 為什麼不先做 ML

目前訓練 collector 資料不完整，且兩類預測都依賴正確的欄位語意、時間對齊與回測。若先做模型，容易得到無法解釋或無法接到產品流程的結果。實作順序應先確保：

- 官方即時資料能被正確取得與發布。
- 使用者查詢的 300 公尺範圍與訓練標籤一致。
- `predictions` 區塊能在資料不足時誠實降級。

## H2 與 MySQL 測試分工

- H2：repository／service 快速測試、狀態轉換、DTO 組裝、基本 JPA mapping。
- MySQL Docker：schema migration、索引、交易、批次寫入、300 公尺候選查詢、快照發布與資料量測。

H2 通過不代表 MySQL 行為完全相同；面試時應主動說明這個邊界。
