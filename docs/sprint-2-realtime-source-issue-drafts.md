# Sprint 2 第三組 GitHub Issues 草案：官方即時來源與快照發布

更新日期：2026-09-26。狀態：草案，尚未建立正式 GitHub Issues，尚未 coding。

## 目標

第二組已把新莊小樣本停車目錄接入 `parking-queries`。第三組目標是讓主系統自己取得新北市官方即時資料，經過正規化、品質檢查與快照發布後，讓使用者查詢讀到可信的目前車位狀態。

此組不使用 `parking-data-collector`，因為該 repo 只作離線訓練資料收集，且目前資料取得方式仍待修正。此組也不做 ML 預測與 Google ETA；Google ETA 會在後續 Google 整合增量處理。

## S2-014：新北市官方即時來源 Client 與原始 DTO

### 範圍

- 建立主系統內的新北市官方 API client 邊界。
- 分別處理路邊停車空位與公有路外停車場即時剩餘車位兩類來源。
- 建立對應原始 DTO，保留官方欄位，不在此 Issue 做最終正規化。
- 支援設定 base URL、timeout、重試次數上限與停用外部呼叫的測試模式。

### 不包含

- 不寫入 MySQL。
- 不發布快照。
- 不接前端。
- 不做 ML 訓練資料。

### 驗收標準

- [ ] 可用測試資料解析路邊與路外官方回應。
- [ ] 外部呼叫 timeout 或失敗時回明確錯誤，不讓主查詢整體崩潰。
- [ ] 設定值可由 YAML／環境變數覆蓋，沒有真實金鑰或秘密進 Git。
- [ ] 文件註明資料來源、官方欄位連結與未確認欄位。

### 測試方式

- 單元測試：以 fixture JSON 驗證 DTO 解析。
- Spring 測試：驗證設定載入與錯誤處理。
- 手動驗收：Sponsor 可在本機 Docker 或 Postman 看到 client health／測試 endpoint 的結果時再定是否需要。

### Human-in-the-loop

- Sponsor 確認官方來源 URL 與欄位頁面是否正確。
- 若要實際打官方 API，Sponsor 確認可接受測試呼叫頻率。

## S2-015：即時資料正規化與資料品質規則

### 範圍

- 將路邊 `cellid`／`cellstatus`／座標／收費與汽車適用性欄位轉成系統統一觀測格式。
- 將路外 `ID`／`AVAILABLE` 等欄位轉成系統統一觀測格式。
- 區分 `AVAILABLE`、`FULL`、`UNKNOWN`、`OUT_OF_SERVICE`、`STALE` 等狀態。
- 保留來源原始值與品質原因，避免日後追查時只剩轉換後結果。

### 不包含

- 不做快照發布交易。
- 不做模型推論。
- 不把未知值補成 0。

### 驗收標準

- [ ] 官方有效 0 位、缺值、特殊值與解析失敗可以分開。
- [ ] 路邊與路外資料都能產生相同結構的內部觀測物件。
- [ ] 未能確認汽車適用性的格位不會被標成可推薦導航。
- [ ] 文件列出欄位映射表與仍待官方確認的欄位。

### 測試方式

- 單元測試：有效值、0 位、缺值、特殊值、未知狀態碼。
- Fixture 測試：使用小型路邊／路外樣本確認轉換結果。

### Human-in-the-loop

- Sponsor 確認狀態文案是否能接受，例如「目前無法確認」與「目前 0 位」。

## S2-016：候選快照寫入與發布交易

### 範圍

- 寫入 `ingestion_run`、候選 `availability_snapshot` 與 `availability_observation`。
- 完整一輪擷取成功且品質門檻通過後，才把快照標成已發布。
- 若來源缺頁、超時或品質不合格，不覆蓋上一輪已發布快照。
- 記錄來源觀測時間與系統取得時間。

### 不包含

- 不做排程器。
- 不做 Redis 刷新鎖。
- 不接前端。

### 驗收標準

- [ ] 成功資料會形成已發布快照。
- [ ] 失敗資料只留下 ingestion_run 與失敗原因，不取代舊快照。
- [ ] 0 位、未知與過期狀態能保留到觀測列。
- [ ] MySQL Docker 驗證 migration、交易與查詢可運作。

### 測試方式

- H2 service 測試：成功發布、失敗不覆蓋、品質原因。
- Docker MySQL 驗證：資料表寫入、索引、交易與查詢。

### Human-in-the-loop

- Sponsor 確認品質門檻初版是否可接受，例如全輪失敗不發布、個別壞值標 unknown。

## S2-017：查詢 API 讀取最新已發布快照

### 範圍

- `parking-queries` 在回傳本地停車目錄時，同步查詢最新已發布快照。
- 依資料年齡回傳目前車位狀態與資料時間。
- 超過 5 分鐘先標示過期，主要目前可用數改為空值，舊數值只作參考。
- 無快照、無對應觀測、有效 0 位與來源失敗分別回不同狀態。

### 不包含

- 不觸發官方來源刷新。
- 不做 Google ETA。
- 不做預測機率。

### 驗收標準

- [ ] 300 公尺內結果可帶出目前車位狀態與資料時間。
- [ ] 過期資料不繼續當成目前可用數。
- [ ] 前端可根據回應區分有位、0 位、未知、過期、未收錄。
- [ ] API 契約文件同步更新。

### 測試方式

- Controller 測試：有效快照、過期快照、無快照、0 位、未知。
- Docker MySQL 驗證：使用 seed 與測試快照資料跑查詢。

### Human-in-the-loop

- Sponsor 以 Postman 驗收回應欄位是否容易理解。

## S2-018：受控刷新與 Redis 協調

### 範圍

- 建立來源級刷新鎖與 cooldown，跨使用者共用同一輪官方擷取。
- 手動刷新與頁面可見時自動刷新都走同一個後端協調流程。
- 進度查詢只讀，不觸發上游。
- 官方來源失敗後記錄錯誤、最後成功時間與下一次可重試時間。

### 不包含

- 不做高頻背景排程。
- 不做模型訓練資料 pipeline。
- 不做遠端部署。

### 驗收標準

- [ ] 多次同時刷新只會形成一輪來源擷取。
- [ ] cooldown 期間不重複打官方 API，回傳既有狀態與下一次可刷新時間。
- [ ] Redis 不可用時系統能降級為保守模式，不因快取失效回假資料。
- [ ] 文件說明 Redis 是協調與短期狀態，不是 MySQL 快照真相。

### 測試方式

- Service 測試：鎖定、cooldown、同時請求、來源失敗。
- Docker Compose 驗證：Redis 正常與停用時的降級行為。
- 手動驗收：連續按刷新，確認後端不重複呼叫來源。

### Human-in-the-loop

- Sponsor 確認初版 cooldown 與過期提示是否符合預期。初版可先用 5 分鐘過期門檻與較保守的來源刷新冷卻，再依量測調整。

## 此組完成後可展示

- 使用者查詢 300 公尺內已收錄停車位置時，可以看到最新已發布的目前車位狀態。
- 官方來源失敗不會覆蓋舊資料，也不會把舊「有位」當成目前可推薦車位。
- 多人查詢或連續刷新不會造成官方 API 被每次查詢放大呼叫。
- API 回應可清楚區分有效 0 位、未知、過期、未收錄與來源失敗。

## 主要風險

- 官方 API 欄位或分頁方式需再次核對，否則正規化規則可能錯誤。
- 新北市來源更新頻率可能約 2～3 分鐘，但系統仍需以實測資料年齡與呼叫限制調整刷新策略。
- Redis 協調只能降低重複呼叫，不能保證官方資料一定最新；畫面仍須顯示資料時間與狀態。
