# 路線圖與一人 Scrum

更新日期：2026-09-24。以下是順序，非已承諾的日期。Sponsor 回報每日約可投入 5–10 小時；20 天約為 100–200 小時，成果仍受 API 資料品質與額度影響。

Sponsor 指定 20 天內完成搜尋、Google ETA、即時車位及路邊／路外抵達時預測，以本機面試展示為第一版。以下為目標時間盒與驗收順序，不是資料品質或外部服務可用性的保證；每日約 5–10 小時，需保留整合與驗證時間。

**2026-09-24 風險與順序調整**：Sponsor 回報獨立訓練 collector 的資料取得方式目前有問題，導致匯出不完整；成因及影響範圍未核實。依 Sponsor 指示先暫緩其樣本盤點與模型驗證，Sprint 1 優先完成主系統即時來源標準化、完整快照／刷新規則、API 與 Docker 契約。20 天內兩類可信預測的目標維持，但此資料依賴使其交付風險升高；若訓練資料無法修復或找到可靠替代，須明確報告未達成，不以虛構機率充數。

**主系統歷史優先順序**：Sponsor 指定 MySQL 和來源呼叫先服務使用者；已發布歷史可供未來離線訓練，但低頻背景取樣只在共用預算與負載允許下進行，缺口如實記錄。具體頻率與容量待主系統量測；不得因訓練需求延遲即時查詢。

## Product Goal

展示新莊目的地搜尋、Google 路線 ETA、附近實際收錄的路邊／路外停車最新觀測，以及兩類可驗證的抵達時預測能力。單一目的地只顯示 300 公尺內實際收錄的類型；無有效訓練標籤或資料不足時明示限制，不編造機率。TDX 作全臺資料入口的長期方向保留，但新莊即時試點以已確認的地方政府來源為主。

## Sprint 0：需求與資料可行性（收尾）

交付：文件、TDX 端點／點數盤點、首份歷史資料小樣本品質報告、統一資料契約草案、MVP 驗收條件。退出條件：知道第一個端點、擷取預算及第一版展示範圍。

## Sprint 1：主系統需求與架構（目前）

交付：目的地搜尋與 Google ETA 需求、路邊區域／路外場站查詢契約、即時來源刷新與品質狀態設計、Google 與政府 API 預算、可驗收的第一個增量。目前先推進不依賴訓練 CSV 的主系統設計；collector 資料盤點暫緩。Sponsor 目前要求先討論，尚未授權主系統 coding。


## Sprint 2 實作順序

已確認開始 coding 後的建議順序：先建立 Spring Boot／Vue／Docker／MySQL／Redis／H2 測試骨架，再做 JPA 資料模型與 API mock，接著完成 300 公尺停車目錄查詢、官方即時來源快照發布、受控刷新、Google 搜尋與 ETA、前端結果頁，最後接預測基準與模型。完整順序見 `implementation-plan.md`。

第一個可展示版本先證明主系統資料流：目的地座標、300 公尺內已收錄位置、目前車位狀態、資料時間、有效 0／未知／過期與 API／前端串接。預測區塊可先顯示資料不足原因，再接有回測依據的機率。
## Sprint 2：主系統第一個端到端增量

待 Sponsor 授權後實作目的地搜尋、起點取得、Google ETA、受控的政府即時資料刷新、附近停車查詢、簡單地圖／清單顯示與失敗狀態。MySQL 保存共同目錄、來源對應、最新啟用快照及可追溯的已發布觀測歷史，供未來離線訓練匯出；歷史保存量與期限待量測。Redis 已列為第一版元件，保存短期查詢進度與經驗證結果的快取。不同來源先經 adapter 標準化，再由主系統 API 提供一致欄位。

## Sprint 3：預測與展示

交付：路邊 300 公尺區域至少一格有位、路外單場有位的兩條預測路徑；歷史資料分析、簡單基準、時間切分回測、可解釋結果與面試展示文檔。若某類資料不足，顯示可量化的限制與「預測資料不足」，不編造機率；該類可信預測未完成時不能宣稱整體 20 天目標已達成。

## 20 天目標時間盒（以實際開發啟動日為第 1 天）

| 日程 | 可展示的增量 | 驗收重點 |
| --- | --- | --- |
| 第 1–3 天 | 鎖定資料欄位、格位適用性、Google／政府請求預算及畫面草圖 | 兩類標籤可驗證；用現有樣本盤點缺口，建立 API 呼叫上限 |
| 第 4–8 天 | 主系統取得、正規化與儲存新莊即時資料；首次無快照及手動更新可用 | 並發查詢共用刷新，失敗保留舊完整快照，0／未知／過期分開 |
| 第 9–12 天 | 地點搜尋、起點、出發時間、Google ETA、300 公尺查詢及本機展示畫面 | 依附近實際收錄呈現路邊／路外；無結果與上游失敗可理解 |
| 第 13–17 天 | 路邊區域與路外場站的基準／預測及時間切分回測 | 各自有明確標籤、訓練／測試時間界線及與簡單基準的量化比較；資料不足時降級 |
| 第 18–20 天 | 端到端驗收、Docker 映像與可重現部署設定、面試展示與風險說明 | 從搜尋到抵達時預測可演示；在乾淨環境啟動容器並驗證 MySQL 持久化／重啟降級；記錄資料年齡、請求量、模型限制及未達成項目 |

這是高壓縮排程。若欄位語意或樣本量在第 3 天仍無法支撐某類預測，須立即記錄阻礙並調整資料取得／模型範圍；不能用隨機機率填補。Docker 可部署性是本期必要交付；實際遠端上線是否在 20 天內完成，待主機資訊與 Sponsor 目標確認。機車留到後續。

## 實作流程與任務管理

PM 會依 `implementation-plan.md` 拆任務，任務需包含範圍、驗收標準、測試方式與 Human-in-the-loop 檢查點。第一版任務可先維護在 Markdown；GitHub 遠端與 Projects 準備好後，再轉成 Issues／Project board。完整流程見 `development-workflow.md`。

Harness 若指 CI/CD 平台，第一版暫不導入；先以 GitHub Issues／Projects 管理工作，以 GitHub Actions 作基本 CI 候選。等 Docker build、測試與部署需求穩定後，再評估 Harness 是否有價值。
## 工作節奏

- GitHub Issue：一件可完成的工作，包含驗收條件。
- GitHub Projects：Backlog／Ready／In Progress／Review／Done，配 Iteration。
- 每個 Sprint 先定目標，結束時展示增量、檢視指標、記錄下一步。
- 小且有意義的 Git commit 應在工作進行時持續建立；完成可運作的小段落就推送到私人或適當權限的遠端，不必等全部做完，也不必每按一次儲存就推送。
- 一人 PR 可作自我審查與面試展示；重大變更先記設計理由。

## Definition of Done 草案

功能符合該 Issue 的驗收條件，資料異常有處理方式，必要測試通過，文件與 `current-state.md` 已更新，金鑰未進 Git，且可從乾淨環境重現。
