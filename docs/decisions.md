# 決策紀錄

以下只記錄已明確採納的方向。草案與尚待驗證的選項請放到 `open-questions.md`。

## 2026-09-23：以 TDX 作為第一個全臺資料入口

- **原因**：先用統一平台盤點全臺可用資料，再依資料缺口增加地方政府 API。
- **影響**：全臺是查詢範圍；即時資料與可預測覆蓋率需逐縣市實測。
- **狀態**：已決定。

## 2026-09-23：建立可維護的資料統一化層

- **原因**：TDX 與地方政府 API 的格式及停車場識別方式可能不同。
- **影響**：來源資料保留原始識別與時間；轉換後使用共同資料契約；路外與路邊資料保留類型差異；前端可以統一呈現。
- **狀態**：已決定；具體資料表仍是草案。

## 2026-09-23：採用一人 Scrum 與 GitHub 管理工作

- **原因**：專案兼具實作與面試展示目的，需要可見的需求、決策、增量與歷史。
- **影響**：文件記方向與決策，Issue 記可執行任務，Projects 管理 Sprint，Git 記變更。
- **狀態**：已決定；Sprint 長度仍可調整。

## 2026-09-23：TDX 介接以官方文件與 Java SampleCode 為依據

- **原因**：避免用過時或第三方的認證與端點範例。
- **影響**：寫 TDX 程式前核對官方 Swagger、費率及 SampleCode。
- **狀態**：已決定。

## 2026-09-23：按 TDX 真實點數計價規劃擷取

- **原因**：免費基礎會員額度有限，服務還有每分鐘存取頻率限制；進階服務與歷史服務單次耗點較高。
- **影響**：先做端點、回應大小及每月擷取次數預算；使用者查詢本地資料，不直接觸發 TDX 擷取。詳見 `tdx-data-and-cost.md`。
- **狀態**：已決定；實際擷取頻率仍待測量。

## 2026-09-23：AI 補值只作估計，不偽裝成即時觀測

- **原因**：來源缺漏時，模型可能提供參考，但無法把缺失的實際車位數變成確定事實。
- **影響**：觀測、估計、未知有不同狀態；資料缺口過大時不預測。
- **狀態**：已決定。

## 2026-09-23：歷史資料先做小範圍 CSV 探索

- **原因**：免費會員每月 3 點；歷史 API 單次日期最多 7 日，完整兩年資料的呼叫及資料量成本高。CSV 容易先在 Jupyter 檢查欄位與資料品質。
- **影響**：先選小範圍資料、申請前確認日期區間與預估耗點；後續可重現擷取再評估 API。Sponsor 已取得新北市路邊格位單日與桃園機場路外 22 日 CSV，兩份資料各自盤點。
- **狀態**：已決定並已取得首批資料；兩筆實扣合計 0.68 點，建模可行性仍待確認。詳見 `historical-data-plan.md`。

## 2026-09-23：第一版同時驗證路邊與路外兩種預測

- **原因**：Sponsor 希望路邊車格和停車場都能預測，並各先完成一個試點。
- **影響**：路邊格位狀態與路外停車場剩餘位各自建模、回測；前端可統一顯示但必須標示類型。新北市路邊格位是第一個資料試點，桃園機場資料是路外候選。
- **狀態**：已決定。

## 2026-09-23：ML 先完成來源統一規格，路外歷史由新北市即時資料累積

- **原因**：TDX 歷史服務 2026-09-23 的停車清單未列新北市路外停車場剩餘位歷史項目；Sponsor 決定改用新北市政府即時資料累積部分跨日樣本。
- **影響**：路邊與路外共用觀測欄位和品質狀態，但分別產生訓練標籤；此 Sprint 的 ML 工作停在來源資料契約和驗證門檻，暫不訓練模型。規格見 `ml-source-contract.md`。
- **狀態**：資料來源及階段順序已決定；個別欄位映射和標籤規則仍待實測。

## 2026-09-23：新莊區先行，獨立收集官方即時資料

- **原因**：完整新北市單月 TDX 歷史檔預估 23.23 點，超過每月 3 點；要盡早累積可用的跨日觀測。
- **影響**：獨立收集器現由 GitHub Actions 定時取得新莊區官方路邊格位與公有路外停車場資料，產生每日 CSV 並存至 Google Drive；它不再提供內部即時 API。主專案的即時查詢資料流須另行設計，並保留 TDX 與地方政府來源統一化。
- **狀態**：已決定；Sponsor 確認排程已運作。來源 ID、資料品質與主專案即時介接仍待驗證。

## 2026-09-24：主系統採依查詢需求調整的共用刷新方向

- **原因**：Sponsor 希望低需求區減少上游呼叫，熱門查詢時提高資料時效；多人查詢仍須共用同一輪擷取結果。
- **影響**：主系統查詢路徑與訓練 collector 分離；無需求時可不刷新。有查詢且快照過期時受控刷新，依來源設定最低間隔及上限；超過既定 5 分鐘顯示門檻必須標示過期。需依來源可篩選的單位衡量熱度，路外動態資料目前不能假設能按地區取得。
- **狀態**：刷新方向已獲 Sponsor 同意；5／3 分鐘動態間隔、60 分鐘預熱、熱度判定與首查等待策略仍待量測及決定。詳見 `realtime-query-design.md`。

## 2026-09-24：第一版讓使用者輸入地址搜尋目的地

- **原因**：Sponsor 指定以地址搜尋作為使用者入口，而非只使用預設目的地或手動輸入座標。
- **影響**：主系統增加地址定位邊界；使用者確認候選後，停車查詢以座標進行。刷新車位資料不重新呼叫地址定位；無匹配、歧義及超出新莊試點範圍須有明確回應。
- **狀態**：已由後續「類 Google Maps 目的地搜尋」需求修正；此筆保留歷史，地址仍是候選輸入之一。詳見 `requirements.md`。

## 2026-09-24：先評估 TGOS 地址定位

- **原因**：Sponsor 同意以 TGOS 作為第一個地址定位候選，先核對申請條件並測試新莊地址的解析品質。
- **影響**：準備代表性的完整地址、不完整地址、無結果及區外案例；比較定位結果、候選歧義、座標系統、延遲與可用條款。地址定位服務介面仍須可替換。
- **狀態**：此優先次序已暫緩：Sponsor 認為預期搜尋體驗更接近 Google Maps，可能不用 TGOS。尚未以核准金鑰進行 API 實測；保留舊評估計畫供追溯。

## 2026-09-24：目的地搜尋轉向類 Google Maps 的互動

- **原因**：Sponsor 說明使用者預期以類 Google Maps 的方式搜尋，並表示可能不採 TGOS。
- **影響**：需求不再限於完整門牌轉座標；評估輸入提示、地標／店名／地址候選、選取後座標，以及是否要地圖互動。TGOS 優先 API 測試暫緩。停車查詢仍只接受已選定的座標，兩種來源額度分開管理。
- **狀態**：搜尋方向已修正；是否直接採 Google Places／Google 地圖、MVP 是否含地圖、成本預算及實際供應者尚未決定。
## 2026-09-24：抵達時間由 Google 路線服務估算

- **原因**：Sponsor 明確要求使用 Google 路線服務提供預計抵達時間，使用者不自行輸入抵達時間。
- **影響**：主系統增加路線 ETA 邊界；預測目標時間取自路線估算並保留計算時刻、起點、目標點、交通設定與失敗狀態。出發點取得方式及是否為每個停車選項計算 ETA 尚待設計。
- **狀態**：提供者與時間來源已決定；Routes 方法、交通設定、費用預算、重新估算頻率仍待驗證。先前文件中「手動輸入抵達時間」的提案由此決策取代。

## 2026-09-24：路線起點同時支援目前位置與手動輸入

- **原因**：Sponsor 指定兩種起點方式都要有；裝置定位被拒絕或不可用時，仍能計算路線 ETA。
- **影響**：手動出發地可沿用目的地搜尋候選流程；裝置位置須由使用者允許取得。兩者最後都轉成已確認的座標，供 Google 路線服務使用，並在結果中標示起點來源。
- **狀態**：已決定；是否立即出發、定位誤差處理與每個停車選項是否另算 ETA 待設計。

## 2026-09-24：未來出發規劃、目的地 ETA 與外部導航

- **原因**：Sponsor 指定預設不是立即出發；產品只評估出發後抵達目的地周邊的有位可能性，不做內建導航。
- **影響**：使用者規劃未來出發時刻，Google Routes 估算抵達搜尋目的地的時間；目的地周圍 300 公尺結果共用此時間作概略預測目標。不逐一計算到每個停車場／格位的 ETA。「立即出發」動作開啟外部 Google Maps 或 Apple 地圖。
- **狀態**：產品方向已決定；出發時間輸入形式、外部地圖選擇介面及 ETA 重新計算規則待細化。先前逐停車選項 ETA 與內建路線展示的提案由本決策取代。

## 2026-09-24：300 公尺內依實際資料類型共同呈現

- **原因**：Sponsor 希望目的地周圍有路邊與路外就一起顯示，只有其中一類時顯示該類。
- **影響**：查詢結果不強制同時存在兩類；每項標示路邊／路外及資料品質。300 公尺的距離計算方法與邊界覆蓋率需另外驗證。
- **狀態**：範圍數值與混合呈現已決定；直線／步行距離、路邊地圖粒度及車種範圍待確認。

## 2026-09-24：Google 服務用途限定於地點搜尋與 ETA

- **原因**：Sponsor 指定 Google 服務在本專案只用於使用者地點搜尋和預計抵達時間估算；導航交由外部地圖。
- **影響**：Google 請求預算聚焦 Places／地圖搜尋及 Routes；停車資料仍取自政府來源，產品內不實作導航。
- **狀態**：用途界線已決定；實際 Google SKU、費用上限與 UI 地圖呈現方式待選型。

## 2026-09-24：300 公尺內按實際資料類型顯示汽車停車選項

- 原因：Sponsor 指定目的地周圍 300 公尺，路邊與路外有哪一種就顯示哪一種；第一版只做汽車。
- 影響：兩類可同頁呈現，各保留資料來源與品質。若只有一類，不虛構另一類；路邊特殊格位的汽車適用性須先核對。
- 狀態：300 公尺、混合呈現與汽車優先已決定；距離方式後續已決定為座標直線距離，見下方「新莊 MVP 以目的地座標方圓 300 公尺驗證」。

## 2026-09-24：出發時間預填當下，可改未來；導航交由外部地圖

- 原因：Sponsor 要 Google 估算到目的地的 ETA，允許使用者規劃未來出發，但產品不做內建導航。
- 影響：出發時間欄位預填當下，可手動改日期和時間；預填當下只計算 ETA，不自動開導航。明確選擇開始導航後才跳轉 Google Maps 或 Apple 地圖。目的地 ETA 是附近停車預測的共同參考時間，不逐一算到停車場入口或格位。
- 狀態：已決定；外部地圖選擇介面及 ETA 重新估算頻率待細化。先前逐停車選項 ETA 提案被此決策取代。

## 2026-09-24：Google 與車位資料的來源分工

- 原因：Sponsor 指定 Google 用於地點搜尋與路線 ETA。
- 影響：車位來源仍是政府 API；外部地圖只承接導航。Google Places、地圖呈現與 Routes 的實際用量各自核算。
- 狀態：用途界線已決定；Google SKU 與費用上限仍待選型。

## 2026-09-24：20 天展示目標包含兩類抵達時預測

- **原因**：Sponsor 指定 20 天內完成前述搜尋、ETA、即時車位與抵達時預測目標，作為面試專案。
- **影響**：路邊建立目的地 300 公尺範圍「抵達時至少一個適用汽車格位可停」的預測；路外建立各收錄停車場「抵達時仍有汽車位」的預測。兩類能力都需有時間切分驗證與資料不足降級；畫面只顯示該目的地實際收錄的類型，不要求每個目的地兩類同時存在。搜尋、ETA、目前車位先形成端到端增量，再加入預測。20 天是交付目標，達成可信度仍須資料品質證據。

## 2026-09-24：路邊以區域機率為主、格位位置為輔

- **影響**：主要顯示 300 公尺圓形範圍內至少一格可停的抵達時機率；次要明細可顯示當前來源回報有位且確認適用汽車的格位位置。明細是目前觀測，不代表抵達時仍有位；狀態碼、合法適用性及座標須先核實。

## 2026-09-24：新莊 MVP 以目的地座標方圓 300 公尺驗證

- **影響**：第一版以座標直線距離 300 公尺作篩選；靠近新莊邊界若未收鄰區資料，需標示覆蓋不完整。此距離不是步行距離。
- **狀態**：MVP 計算方向已決定。

## 2026-09-24：無快照與手動更新走受控共用刷新

- **原因**：Sponsor 希望首次查詢直接取得新北市政府即時資料，並提供重新整理機制；多人使用時仍需控制官方請求。
- **影響**：首次沒有可用快照時，主系統啟動該來源一次共用擷取並在等待上限內回傳結果；若失敗或逾時顯示暫無即時資料。手動更新先檢查共用快照，仍有效則回傳；過期且符合最低間隔／預算時啟動一次共用擷取。並發使用者共用該次結果，失敗不覆蓋上一份完整快照。重新整理不能保證每次都呼叫官方來源或現場有位。
- **狀態**：流程已決定；等待上限、最低間隔及預算值待實測。

## 2026-09-24：面試先本機展示

- **原因**：Sponsor 預計面試時在本機展示；公開網址只在需要其他人遠端測試時再規劃。
- **影響**：第一版部署及展示以本機可重現為驗收，外部測試的公開部署另作後續工作；Google 金鑰與服務用量仍須控管。
- **狀態**：面試展示方式可保留；後續 Sponsor 已補充 Docker 為必要交付，未來要部署到其他伺服器。請以下方較新的部署決策為準，不再視為僅需本機部署。

## 2026-09-24：搜尋後地圖與結果清單同頁呈現

- **原因**：Sponsor 希望搜尋目的地時有類似 Google Maps 的候選體驗，選定地點後地圖與停車結果在同一頁同時顯示。
- **影響**：前端需求固定為地圖加清單並存，兩者需能對應目的地、路邊區域及路外場站；實際收錄哪一類就顯示哪一類。類似 Google Maps 的搜尋體驗不等於已決定地圖底圖、Places 接法或前端框架。
- **狀態**：呈現方向已決定；手機布局、標記與清單連動、Google 服務選型和費用仍待確認。

## 2026-09-24：電腦版第一版採地圖優先的結果呈現

- **原因**：Sponsor 希望先在地圖探索目的地周圍選項，點簡要標記後再看詳細結果，並同意保留固定的路邊區域機率摘要與「查看全部結果」入口。
- **影響**：電腦版初始不常駐完整清單；地圖和區域摘要先可見，完整結果由明顯入口或標記詳情面板打開。手機版仍以地圖在上、清單在下。兩版都維持同頁有地圖與可取得的結果清單；路邊機率不由單一格位標記代表。
- **狀態**：Sponsor 看過常駐清單與地圖優先草圖比較後，同意以地圖優先作第一版方向；面板尺寸、標記密度與導航按鈕互動仍須原型驗證。見 `ui-wireframe-comparison.md`。

## 2026-09-24：路邊格位小資訊卡直接提供外部路線入口

- **原因**：Sponsor 希望點選目前回報有位且已確認適用汽車的格位後，不必先開完整清單即可前往該位置。

- **影響**：`parking_place` 保存 WGS84 經緯度並建立服務區、類型、狀態與經緯度索引；Repository 依外接矩形取得候選，application service 再計算精確直線距離並連接各來源已發布快照。前端只接收後端整理好的距離、覆蓋、目前觀測和預測狀態，不自行判斷 300 公尺範圍。
- **狀態**：第一版查詢策略已決定；實際索引欄位順序、候選數、查詢延遲、排序／分頁和是否升級 MySQL spatial 仍待實測。沒有 coding。
## 2026-09-25：Redis 第一版只保存短期狀態、協調與可重建快取

- **原因**：Sponsor 要第一版納入 Redis，但主系統同時需要可追溯歷史、可靠快照發布與官方來源用量控制；Redis 不適合成為唯一真相。
- **影響**：Redis 保存 `queryId` 進度、防重送 token、來源刷新短鎖／進度，以及含快照版本的附近結果或摘要快取。MySQL 仍是停車目錄、已發布快照、來源冷卻、用量與訓練歷史的事實來源。Redis 過期或重啟時，短期查詢可失效並提示重新規劃，但已發布車位資料仍可由 MySQL 回答或標示過期。
- **狀態**：Redis 職責與 key 類型已記錄於 `redis-design.md`；實際 TTL、容量、序列化格式、owner token／心跳、多實例鎖安全性與快取命中率仍待實測。沒有 coding。
## 2026-09-25：第一版部署採單台伺服器 Docker Compose 候選

- **原因**：Sponsor 指定 Docker 是必要交付且未來會部署到其他 server；目前 MVP 尚不需要 Kubernetes 或多台主機複雜度。
- **影響**：第一版候選服務為 `web`、`api`、`mysql`、`redis`。`web` 提供 Vue build 後靜態頁並代理 `/api`；`api` 執行 Spring Boot；`mysql` 使用 volume 保存目錄、快照、觀測歷史與來源狀態；`redis` 保存短期查詢進度、刷新協調與可重建快取。對外只開 `web`，機密以環境變數或部署端 `.env` 注入，不寫入 Git 或 image。
- **狀態**：部署拓樸候選已記錄於 `docker-deployment.md`；實際 Dockerfile、compose、版本、HTTPS 入口、備份流程、目標主機與模型產物放置方式仍待實作前決定。沒有 coding。
