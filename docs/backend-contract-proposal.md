## 第一個後端邊界

使用者選定目的地與出發地、確認出發時間後，主系統回答：「預計何時抵達目的地？目的地方圓 300 公尺內，實際收錄了哪些汽車停車選項？目前來源回報什麼？抵達時有位機率是多少？資料可信狀態如何？」瀏覽器負責畫面與互動；主系統負責資料驗證、政府來源受控共用刷新、周邊查詢、Google 路線 ETA 和預測結果組合。獨立 collector 只供訓練，不作即時查詢來源。

## 候選的呼叫責任

| 行為 | 建議責任 | 待確認 |
| --- | --- | --- |
| 類 Google Maps 的目的地／手動起點候選 | 若採 Google Maps JavaScript／Places 元件，可在瀏覽器提供候選並取得使用者選定座標；此方案使用受網站限制的專用金鑰 | 實際搜尋供應者、選取後欄位、用量與顯示條款 |

| Google Routes 駕車 ETA | 建議由 Spring Boot 封裝 Routes Web Service，伺服器憑證不傳到瀏覽器，記錄請求量與失敗；只算到搜尋目的地 | 交通模式、未來出發時間、重新估算頻率、預算 |
| 新北市／TDX 停車即時資料 | 只由主系統 Spring Boot 的來源介接器獨立取得，按資料集共用快照／受控刷新；瀏覽器與訓練 collector 均不供應主系統快照 | 來源最小間隔、首查等待、主系統實際上游用量 |

| 外部地圖路線 | 使用者點小卡後開 Google Maps／Apple Maps 到已核實的格位座標 | 格位座標、車種資格與資料時效 |

Google 官方安全指引要求網頁端與 Web Service 憑證依使用位置限制並保護伺服器金鑰；此表是候選分工，不表示 Google Places 或地圖底圖已選定。見 [Google Maps Platform security guidance](https://developers.google.com/maps/api-security-best-practices)。

## 主查詢的輸入（語意草案）

| 輸入 | 用途／規則 |
| --- | --- |
| 已選定目的地座標與可辨識名稱／來源識別 | 後端核對座標範圍；不能由文字名稱直接猜第一個候選 |
| 已選定起點座標與起點來源 | 來源為裝置定位或手動選取；不把使用者原始搜尋文字當成完整可信座標 |
| 預計出發日期時間 | 預填當下但可改未來；儲存與傳輸需有時區或明確 UTC 語意 |
| 查詢範圍 | MVP 固定目的地直線半徑 300 公尺，不允許任意放大使官方呼叫量失控 |

使用者不傳入自算的 ETA 或「有位機率」。主系統可以把 Google 地點選取與停車查詢分成不同請求，但重整車位不得重新做地點搜尋。

## 主查詢的輸出（語意草案）

| 區塊 | 至少包含 |
| --- | --- |
| 目的地與路線 | 目的地座標、起點來源、出發時間、Google 估計抵達時間、路線計算時間及有效／失敗狀態 |
| 查詢範圍 | 300 公尺圓心與半徑、資料覆蓋範圍／新莊邊界提示 |
| 路邊區域 | 是否收錄、抵達時至少一格可停機率或不足原因、模型時間／版本、目前適用格位觀測數與資料品質 |
| 路邊格位明細 | 只有已核實適用汽車且有效觀測的格位可顯示「目前有位」；格位 ID、座標、來源與取得／觀測時間，供小卡與外部路線使用 |
| 路外停車場 | 每場 ID、名稱、位置、目前汽車剩餘位及品質、抵達時有位機率或不足原因、模型時間／版本 |
| 來源狀態 | 路邊與路外各自的成功取得時間、來源觀測時間（若有）、刷新中／失敗、完整性與品質理由；不能把 0、未知與過期合併 |

Google ETA、路邊、路外與預測可各自失敗。回應不因單一來源失敗就把其他有效區塊丟掉；畫面按結果狀態分別呈現。模型缺即時特徵時是否仍可推論須由回測決定。

## 2026-09-24 首輪 API 契約討論（提案，未定案）

前端已選 Vue 3＋Vite，後端採 Spring Boot Web／Spring MVC REST。建議把「規劃一次行程」與「只更新車位」分成兩種動作，避免使用者按重新整理時又消耗一次 Google 地點搜尋及 Routes ETA 呼叫。

| 動作 | 前端送出 | 後端回傳 |
| --- | --- | --- |
| 規劃行程 | 使用者選定的起點／目的地座標、可辨識地點資訊、帶時區的出發時間；汽車與 300 公尺由 MVP 後端固定 | 到目的地的 ETA 狀態與抵達時刻、300 公尺覆蓋狀態、路邊區域與格位明細、路外場站、各來源目前觀測和抵達時預測狀態 |
| 重新整理車位 | 已選定的目的地座標／查詢範圍識別；沿用行程的抵達時刻，不重新搜尋地點或計算路線 | 路邊／路外更新後的目前車位與資料品質；只有模型需要且符合既定推論規則時才更新預測 |

主查詢建議在等待上限內平行進行 ETA 與兩種來源的快照檢查／受控刷新。三部分各自標示成功、失敗或逾時；一個來源失敗不抹掉其他有效結果。若 ETA 失敗，仍可回傳目前車位及位置，但抵達時預測標示「暫時無法估算」。若附近沒有收錄路邊或路外，回傳「未收錄該類型」，不把它表達成 0 位。若來源回報明確 0 位，這是有效觀測。

兩種動作都先讀主系統的共用完整快照；過期時按最低刷新間隔、共用鎖與預算決定是否等待一輪上游刷新。重新整理不等於強制呼叫政府 API。回應至少帶每類來源成功取得時間、可空的來源觀測時間、有效／過期／未知狀態、刷新失敗理由；格位有位與外部路線入口只在汽車適用性、座標及時效可驗證時出現。預測與觀測各自標示時間／版本，不混合。

**待收斂**：具體路由、JSON 欄位、驗證錯誤格式、前景等待與背景作業上限、ETA 快取／重新估算條件，以及前端查詢本系統刷新狀態的契約。先回已完成區塊、車位完成後自動補上已由 Sponsor 決定。

## 2026-09-24 首查等待與部分結果（互動已決定，數值待驗證）

- 前端選定目的地後立即顯示目的地、300 公尺範圍與各區塊「計算中／更新中」。ETA、路邊、路外各自完成就能呈現狀態，不要求三者同時成功。
- 快照在 5 分鐘測試時效內且品質有效時，直接回傳本地結果；沒有快照或已過期時，按來源啟動一輪共用受控刷新。等待上限須量測**主系統自己**完成整輪擷取及驗證的時間，不能由另一個程式的單次 HTTP 逾時推得。
- 已決定：先呈現已完成的 ETA、目的地與已收錄且位置可信的停車選項；車位未完成時標「更新中」，由前端查詢**本系統**的刷新狀態，完成後自動補上。進度查詢不得重做 Google ETA 或觸發新一輪政府呼叫。沒有可用停車目錄時只顯示目的地與 300 公尺範圍，不捏造格位位置。約 10 秒前景等待只是待實測的原型候選，不是服務承諾。
- 刷新最後失敗或超出背景作業上限時，顯示「目前車位無法確認」與最後成功取得時間；舊「有位」格位不得繼續作目前推薦。若 ETA 失敗，仍可顯示可用的目前車位，但抵達時預測暫停。
- 待決：前端查詢本系統狀態的路由、輪詢間隔與停止條件、前景等待上限、背景作業總時限，以及哪些來源的延遲／失敗率足以支持具體數字。

## 2026-09-24 漸進式查詢的 API 語意（設計提案）

為實現 Sponsor 已選的「先看 ETA 與位置，車位完成後自動補上」，建議一次查詢建立短期 `queryId`。此 ID 代表一趟已選定起點、目的地、出發時間的查詢狀態，不代表車位預約或永久保存個人行程。

| 呼叫語意 | 回應與副作用 |
| --- | --- |
| 建立行程查詢 | 驗證起訖座標與出發時間，立即回 `queryId`、目的地、300 公尺範圍與本地已收錄且位置可信的目錄；同時安排一次 Google ETA 及所需來源的受控共用刷新。若已有有效快照，直接附上目前觀測。 |
| 讀取查詢進度 | 只讀 `queryId` 對應狀態，回 ETA、路邊、路外、預測各自的 `pending`／`ready`／`unavailable`／`failed` 和已完成結果。此呼叫不得觸發 Google 或政府 HTTP 請求。 |
| 使用者手動更新車位 | 檢查路邊／路外共用快照及來源最低間隔，必要時加入已進行中的刷新或啟動一次新刷新；沿用行程 ETA，不重做地點搜尋或路線。 |

Vue 可在尚有 `pending` 區塊時，以約 2 秒為**原型候選**查詢本地進度，完成、失敗、離開頁面或達 UI 上限便停止。這些本地查詢不增加上游 API 用量，但仍要有限制，不能無限輪詢。Spring Boot 對同一政府資料集維持一個共享刷新任務；不同 `queryId` 可以共用刷新結果，但各自行程的 Google ETA 仍按起訖點和出發時間計算，避免把別人的行程 ETA 直接套用。

前端先顯示已取得的 ETA；若 ETA 尚未完成，只顯示「路線計算中」，但地圖和已可信的停車位置不用等。只知道位置而沒有新鮮車位時，標記使用中性位置樣式，不顯示「目前有位」或導向空位的推薦。路邊與路外彼此獨立完成；有效 0 位、未收錄、過期與抓取失敗維持不同狀態。

待驗證：是否採短期查詢狀態與 `queryId`、保留期限及重啟處理；具體路由與 HTTP 狀態碼；本機進度輪詢間隔／上限；Google ETA 的請求預算；來源整輪刷新耗時的 p50／p95、錯誤率與逾時。若實測刷新很快，可簡化交互，但前端的分區塊狀態契約仍保留。

## 2026-09-24 短期查詢狀態與重啟（設計提案）

第一版本機單實例建議分開保存三種狀態，因為它們的有效期間與服務對象不同：

| 狀態 | 建議位置 | 理由與重啟後處理 |
| --- | --- | --- |
| 每位使用者的短期查詢：`queryId`、起訖座標、出發時間、ETA／預測進度 | Redis，設定期限與容量上限；不長期保存原始搜尋文字或個人路線 | Redis 鍵過期或 Redis 失效時，Vue 收到查詢已失效提示並重新查詢；重新查詢 Google ETA 才可能再次計費。Spring Boot 重啟時仍須處理未完成工作，不能讓查詢永遠停在 `pending`。 |
| 共享的停車目錄、最新**完整且驗證通過**的來源快照、最後成功取得時間 | MySQL／JPA；快照版本在完整驗證後才發布 | 重啟後仍可讀取；超過 5 分鐘測試門檻就標過期，不能因重啟重新計時或把舊「有位」標成最新。 |
| 每來源的上次擷取、下次可擷取時間、用量與失敗紀錄 | MySQL；本機記憶體只持有執行中的單一刷新協調與鎖 | 重啟後仍遵守來源最低間隔／預算，避免進程一重啟便立即多抓。重啟會中斷進行中的刷新，未完成的資料不發布。 |

Sponsor 後續指定第一版加入 Redis；短期查詢進度與已驗證結果快取改由 Redis 承擔，取代先前僅放 Spring Boot 記憶體的方案。仍須限制同時查詢數、鍵期限、容量與輪詢速率；Redis 存在不代表刷新鎖已通過多實例驗證。MySQL 保留完整快照、來源冷卻與用量的持久紀錄。

Sponsor 已指定 Redis、MySQL 與 Docker 都納入第一版；見 `decisions.md` 和 `backend-stack-and-normalization.md`。仍待確認：短期查詢保留期、逾時／錯誤回應語意、未來是否需要多實例，以及容器打包方式。

## Docker 遠端部署架構（必要交付；具體拓樸待定）

Docker 映像與可重現部署設定已是必需。若目標是一台可自行管理 Docker 的伺服器，建議先評估 Compose：一個 Spring Boot 應用容器、一個 MySQL 容器、一個 Redis 容器；Vue 3／Vite 的正式建置檔可由 Spring Boot 作靜態頁面提供，讓瀏覽器同源取得頁面與 REST API。遠端另需 HTTPS 入口，可用主機既有反向代理或新增代理容器；若需分離前端發布週期，再比較獨立前端容器。這些是部署拓樸候選，不能將實際伺服器種類視為已知。

MySQL 使用持久化 volume 保存資料並規劃備份／還原；Redis 存短期 `queryId` 進度，Spring Boot 容器重啟時進行中的工作中斷，舊查詢須有逾時／失敗語意，不能永遠顯示 `pending`。新查詢仍依 MySQL 原快照取得時間判斷是否已超過 5 分鐘。容器啟動須檢查 MySQL 與 Redis 健康狀態；兩者不直接公開於網際網路，金鑰與資料庫密碼由部署環境／秘密管理提供，不放入 image 或 repository。遠端裝置定位需要瀏覽器安全環境（通常為 HTTPS），Google 網頁端與伺服器端憑證依用途和網站／來源限制。實際遠端上線時點、主機、網域、備份位置及是否多實例仍待確認。尚無 Dockerfile／Compose 實作。
