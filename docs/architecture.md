# 系統架構草案

更新日期：2026-09-23。尚未實作。

## 資料流

`TDX／未來地方政府 API → 來源介接器 → 欄位轉換與驗證 → MySQL 最新狀態／歷史快照 → Spring Boot 查詢／預測 → 網頁`

Redis 預計快取熱門查詢與最新可顯示資料；它不是額度保護的唯一機制。排程擷取與使用者查詢需分離，避免人數增加直接放大 TDX 呼叫量。額度保護另需排程預算、速率控制、重試上限及單一擷取者。

## 統一資料契約（草案）

- `parking_place`：系統內 ID、類型（路外停車場／路邊格位或路段）、名稱、位置、可選入口、車種與可選總車位。
- `source_mapping`：資料來源、來源停車場 ID、對應的系統內 ID、對應信心及人工檢查狀態。
- `availability_observation`：來源回報的剩餘車位、車種、來源更新時間、系統取得時間、原始資料參照。保留原始值，不讓模型改寫。
- `prediction`：目標抵達時間、有位機率或風險、模型版本、產生時間、資料品質狀態。
- `ingestion_run`：擷取端點、開始與結束時間、成功／失敗、筆數、回應大小、估算耗點。

「0 位」是有效觀測；缺值是沒有有效觀測；過期是觀測曾有效但超過新鮮度門檻。模型推估是另一種資料，不與觀測混為一筆。新鮮度門檻依端點更新情況實測後定義。

## AI 補足缺漏的邊界

短暫中斷且有足夠歷史時，可提供標為「估計」的結果與可信度；若長時間中斷、特別事件或新停車場沒有歷史，回傳「無法可靠預測」。不能把補值當成模型驗證時的真實答案，否則評估會失真。

## 技術方向

Java／Spring Boot 單體、MySQL＋Spring Data JPA、Redis、Docker；Jupyter 只用於探索與離線模型實驗。大量快照若 JPA 批次寫入不佳，量測後再局部改用批次 SQL。前端先以易維護的簡單網頁為主，路線服務延後決定。
