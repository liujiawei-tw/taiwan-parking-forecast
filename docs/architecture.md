## 資料流

`TDX／未來地方政府 API → 來源介接器 → 欄位轉換與驗證 → MySQL 最新狀態／歷史快照 → Spring Boot 查詢／預測 → 網頁`

Redis 已由 Sponsor 指定加入第一版，供短期查詢進度與經驗證結果快取；它不是額度保護的必要或唯一機制。來源擷取與使用者查詢需分離，避免人數增加直接放大上游呼叫量。額度保護另需最低間隔、預算、速率控制、重試上限及單一擷取者。

## Sprint 1 主系統設計提案（未定案）

- 第一個可展示增量：新莊目的地附近同時列出路邊區域與路外停車場，分開標示類型，顯示最新觀測、資料來源時間及有效／過期／未知。資料不足時不顯示虛構預測。
- 查詢 API 輸入候選：目的地座標、搜尋範圍、預計抵達時間。展示介面可先用新莊預設目的地或地圖選點；自由輸入地址的地理編碼服務尚未選定。
- **用戶即時查詢流程獨立於訓練 collector。**主系統從新北市官方即時來源、之後按額度從 TDX 取得最新觀測；標準化後保存於 MySQL 並供用戶查詢。使用者需求刷新與低頻定時取樣共用來源級受控流程；使用者服務優先，背景取樣在預算或負載不足時可略過。資料超過門檻且來源最低間隔與預算允許時，只由一輪擷取服務同時請求，不逐人呼叫上游。用戶接近抵達時的手動更新也走同一套限制。背景頻率與實際來源間隔待實測。
- **模型訓練流程**由獨立 collector 的 GitHub Actions 目前每 30 分鐘排程擷取並產出每日 CSV 至 Google Drive；其任務是累積歷史觀測，不是用戶即時資料來源，也不提供即時查詢 API。兩條流程都可能呼叫新北市上游，需分開計量並限制主系統呼叫；不以訓練 CSV 回答『現在有沒有位』。
- 路邊的搜尋範圍必須與後續 ML 區域標籤定義一致；路外以單一停車場為結果。跨來源 ID 尚未核對時不可逕自合併。Redis 已納入第一版，快取粒度與容量仍待實測。

## 新鮮度與呼叫控制（設計提案）

- 『最新』分成來源觀測時間、系統成功取得時間、使用者查詢時間。若來源不提供觀測時間，只能聲稱系統何時取得，不能保證現場狀態同樣新。回應保留時間與 `fresh`／`stale`／`unknown` 狀態。
- 主系統的最低刷新間隔依來源更新頻率、實測變動與介接限制設定；新北市資料集頁分別標示路邊每 2 分鐘、路外每 3 分鐘更新，但不保證每筆資料都如此新。離線訓練排程與用戶查詢時效無關。
- 後端受控刷新：只有資料超過門檻、距上次呼叫達最低間隔且預算允許，才讓一個請求啟動刷新；其他同時請求等待同一結果或收到標明時間的舊資料。刷新逾時／失敗時保留舊資料及錯誤狀態，不把它顯示成最新。
- Redis 存放短期查詢進度及經驗證的近期結果；多實例刷新鎖仍須另行設計和驗證。來源最短刷新間隔、完整快照與用量紀錄持久保存在 MySQL。Redis 本身不會令上游資料更新，也不能取代月度 TDX 點數預算。
- 擷取一輪不等於一個 HTTP 請求；主系統要量測自己選定端點的分頁、重試、資料量及耗時。需求觸發可讓主系統無人使用時接近零次，高流量則以共用刷新與最低間隔設上限。TDX 基礎停車服務若單端點每 5 分鐘輪詢，僅計次 30 天就約 5.76 點，尚未計量，超過 Sponsor 每月 3 點；不能照搬新北市來源的頻率到 TDX。離線訓練收集器的運作量另見 `training-collector-operations.md`，不作主系統即時負載估算。細節見 `realtime-query-design.md`。
- 以上門檻與頻率是待測提案；Sprint 1 先量測成功擷取間隔、來源資料時間、使用者可見資料年齡、上游呼叫數和失敗率，再設定可驗收的新鮮度目標。

## 統一資料契約（草案）

- `parking_place`：系統內 ID、類型（路外停車場／路邊格位或路段）、名稱、位置、可選入口、車種與可選總車位。
- `source_mapping`：資料來源、來源停車場 ID、對應的系統內 ID、對應信心及人工檢查狀態。
- `availability_observation`：來源回報的剩餘車位、車種、來源更新時間、系統取得時間、原始資料參照。保留原始值，不讓模型改寫。
- `prediction`：目標抵達時間、有位機率或風險、模型版本、產生時間、資料品質狀態。
- `ingestion_run`：擷取端點、開始與結束時間、成功／失敗、筆數、回應大小、估算耗點。

「0 位」是有效觀測；缺值是沒有有效觀測；過期是觀測曾有效但超過新鮮度門檻。模型推估是另一種資料，不與觀測混為一筆。新鮮度門檻依端點更新情況實測後定義。

## AI 補足缺漏的邊界

短暫中斷且有足夠歷史時，可提供標為「估計」的結果與可信度；若長時間中斷、特別事件或新停車場沒有歷史，回傳「無法可靠預測」。不能把補值當成模型驗證時的真實答案，否則評估會失真。

## 技術方向

Java／Spring Boot Web（Spring MVC REST）單體、MySQL＋Spring Data JPA、Redis、Docker；前端已選 Vue 3＋Vite。Redis 已由 Sponsor 指定納入第一版，負責短期查詢進度與經驗證資料的快取，MySQL 仍是完整快照與呼叫控制的持久真相；細節見 `backend-stack-and-normalization.md`。Jupyter 只用於探索與離線模型實驗。大量快照若 JPA 批次寫入不佳，量測後再局部改用批次 SQL。Google Routes ETA 已列入第一版；地圖與地點搜尋的實際服務仍待選型。本段技術方向不代表應用程式已實作。

## Sprint 1 主系統模組邊界（2026-09-24 討論稿，未實作）

採單一 Spring Boot 應用、內部分模組的起步架構；新莊 MVP 不需先拆成多個服務。訓練 collector 仍是獨立專案，僅輸出供後續 ML 使用的歷史樣本，不負責主系統即時回應。

| 模組 | 責任 | 不承擔的事 |
| --- | --- | --- |
| 查詢入口 | 驗證目的地座標、搜尋範圍、預計抵達時間；組合路邊與路外結果 | 不在每次查詢中直接執行所有來源 HTTP 呼叫 |
| 停車目錄 | 保存停車場／格位的穩定 ID、位置、類型、車種、來源對應；支援附近篩選 | 不把名稱相同直接視為同一實體 |
| 來源介接與正規化 | 各來源轉成有來源 ID、原值、品質狀態與時間的共同觀測；保留原始資料參照 | 不把來源缺值或負值轉成 0 |
| 刷新協調 | 依來源控制最低間隔、單一擷取者、請求預算、重試上限；完整驗證後發布快照 | 不因每位使用者查詢而個別刷新 |
| 最新觀測查詢 | 從已發布快照讀取附近資料並判斷有效／過期／未知 | 不從訓練 CSV 或 collector 取得「即時」答案 |
| 預測介面 | 日後接入模型結果，保留模型版本、目標時間和資料品質 | 在尚無可靠模型時不產生假預測 |
| 用量與品質監測 | 記錄每來源 HTTP 次數、耗時、失敗、最新快照年齡和查詢等待 | 不以估算請求量充當實際用量 |

動態快照以來源資料集為單位刷新，附近篩選在本地執行。路邊結果對使用者按固定版本的地理範圍彙整，路外仍為單一停車場；兩者在統一回應中分別標示類型與可觀測範圍。路邊碼表及格種適用性尚未核實前，不宣稱「可合法停放」數量。來源逐筆觀測時間缺失時，只呈現系統成功取得的時間。

資料儲存先分為：MySQL 的停車目錄與來源對應、每來源已發布快照及可追溯歷史觀測、刷新執行紀錄；Redis 的短期查詢進度與經驗證結果快取。依 Sponsor 新要求，主系統成功發布的運行歷史也須能供未來離線模型訓練；獨立 collector 仍是另一條資料管線，不參與用戶查詢。線上只讀啟用版本，訓練日後從合格歷史匯出；歷史保留期、容量／歸檔及是否另設受預算控制的定時取樣待量測，不預設無限保存。MySQL／JPA 先承擔目錄和查詢；大量資料寫入效能若量測不足再處理。單實例可先由應用內鎖協調刷新，跨實例鎖須另行驗證。

第一個端到端展示範圍建議是：以新莊預設目的地或座標查詢附近路邊區域及路外停車場，標示最新觀測、取得時間、資料品質與來源；尚無可靠模型時回傳「暫無預測」。自由地址搜尋需地理編碼來源，模型推論需另定介面與部署方式，兩者不阻塞即時查詢的第一個可展示增量。API 輸入輸出、路邊搜尋範圍、首次查詢等待上限與部署方式仍待 Sponsor 確認。

驗收時至少檢查：兩位同時查詢只造成一輪來源刷新；刷新部分失敗不發布混合快照；有效 0 位、未知與過期在回應中不同；來源缺觀測時間時 UI 不冒稱官方更新時間；記錄合併 collector 後的上游請求量。

## 地址搜尋入口（2026-09-24 設計草案）

使用者輸入地址 → 地址定位服務回傳候選地址與座標 → 使用者確認候選 → 主系統用確認後的座標查附近路邊區域／路外停車場 → 後續刷新只更新車位觀測。地理編碼與政府停車資料來源各有獨立額度、錯誤處理與監測，不讓每次手動更新車位都再次消耗定位請求。

在應用內設「地址定位」介面以隔離供應者；輸出至少包含標準化顯示地址、座標、座標系統、定位精度／匹配品質與供應者。主系統只以已核對的共同座標系統計算距離；地址不明確時讓使用者選擇，不自動採用第一個候選。新莊 MVP 對區外結果顯示「目前尚未支援此區」，不能誤報附近沒有停車位。先由按下搜尋才定位，避免每個輸入字都發出請求；是否做地址快取須遵守選定供應者的條款，避免長期保存不必要的使用者查詢地址。

官方候選來源：TGOS MAP API 有地址定位功能，官方文件稱申請使用免費，但需 TGOS 帳號、申請核准及網域／IP 驗證；Google Geocoding 需啟用計費並按請求收費。內政部國土測繪中心部分門牌／模糊搜尋 API 需申請。供應者尚未定案，需以實際新莊地址測試解析率、座標精度、延遲、額度與可用條款。地圖底圖選型與地址定位可以分開決策。

## 2026-09-24 目的地搜尋修正（取代上節地址優先方案）

Sponsor 希望像 Google Maps 一樣搜尋目的地，TGOS 優先評估暫緩。上節「只輸入地址、按搜尋才查詢」保留為討論歷史，不作目前產品方向。新候選流程為：輸入目的地關鍵字 → 顯示可辨識的地址／地標／店名候選 → 使用者選定 → 取得地點座標 → 後端以座標查附近停車選項。刷新停車資料不再呼叫地點搜尋。是否顯示互動地圖、是否直接使用 Google 服務仍待 Sponsor 明確界定。

架構維持「目的地搜尋」與「停車即時資料」分離的邊界。若使用 Google Places Autocomplete (New)，官方 Widget 可提供候選與選取後地點資料；依取得欄位與會話結束方式，Autocomplete、Place Details、地圖呈現有不同計費與授權要求。不能把「像 Google Maps 的搜尋體驗」直接視為已購買 Google Maps 平台或免費無限使用。選型前比較台灣地點覆蓋、候選品質、使用者確認方式、預估請求與費用、配額、金鑰保護及資料展示／保存規則。

第一個展示增量須支援使用者搜尋並選取目的地，不能再以預設座標作為唯一正式入口；可用固定測試地點做內部驗證，不算滿足產品需求。

## 2026-09-24 Google 路線 ETA 修正

Sponsor 不希望手動輸入抵達時間；原先目的地查詢中的 `arrivalAt` 不再是使用者必填欄位。增加路線 ETA 模組，接收出發點、選定目的地／停車選項、出發時間及交通設定，回傳估計時長、抵達時刻與品質狀態。路線模組與地點搜尋、政府停車快照刷新各自控制請求與額度。Google Routes 方法、出發點與每個停車選項的 ETA 粒度仍在設計，詳見 `route-eta-design.md`。上文「使用者輸入預計抵達時間」為舊提案，已由本節取代。
