# 用戶即時停車查詢與刷新規格（Sprint 1 設計草案）

更新：2026-09-24。狀態：主系統設計討論中；尚未實作。本檔只定義使用者即時查詢；離線訓練資料收集器的運作另見 `training-collector-operations.md`，不參與本流程。

最新前後端契約提案見 `api-contract-v1-draft.md`：建立查詢先回 `queryId`、可信位置與進度，ETA／來源工作非同步完成。以下早期「約 10 秒前景等待」文字保留討論歷史，已由非同步立即回應方向取代；具體背景期限仍待主系統實測。

## 要解決的問題

使用者查詢新莊目的地附近停車選項時，顯示主系統目前可取得的最新觀測及其時間，同時避免每位使用者各自呼叫新北市／TDX 上游。即時觀測與抵達時預測分開；第一個可展示增量先做觀測查詢，ML 待資料品質驗證後接入。

## 主系統即時查詢的邊界

Spring Boot 主系統須自己介接新北市官方即時來源，保存已驗證的共用快照並回答使用者；未來 TDX 來源另按點數預算設限。訓練 CSV、Google Drive 與獨立 `parking-data-collector` 不在即時請求鏈內，主系統不呼叫它的 API，也不以它的排程或時間戳判斷資料新鮮度。兩個獨立系統若使用同一官方平台，僅需在營運層面評估平台總流量；不因此共用程式、快照或資料庫。

## 來源頻率與一輪擷取的實際成本

新北市資料集頁標示：路邊格位約每 2 分鐘更新，公有路外剩餘位約每 3 分鐘更新。這是資料集發布頻率，不能保證每一格、每一場的觀測都剛更新。主系統須自行記錄完整快照成功發布時間；若來源有可靠逐筆觀測時間，也要分開保存。

主系統尚未選定整檔或分頁取得方式，須對正式介接端點實測一輪的 HTTP 次數、資料量與延遲；路外靜態目錄另訂較長更新週期，不隨每次動態刷新重抓。**一次邏輯刷新可能包含多個 HTTP 請求**，計量與失敗處理都以主系統自己的實際請求為準。新北市開發指引對大量、高頻介接有提醒，實際刷新策略仍須核對來源限制。

## 主系統查詢與受控刷新

1. 以來源資料集為刷新單位，共用一份新莊路邊快照與一份路外快照；不依每位使用者的目的地或半徑分別擷取。目的地附近篩選在主系統完成。
2. 查詢時先看快照的 `last_successful_fetch_at`、來源觀測時間（若有）、資料完整性及 `next_allowed_fetch_at`。**未到最低刷新間隔**時直接回覆；一到允許刷新時間，下一個查詢可啟動**一次**該來源刷新，其餘同時查詢共用結果。刷新觸發門檻與畫面標示「過期」的 5 分鐘門檻是兩個不同設定。
3. 第一次查詢而沒有快照時，嘗試刷新並設等待上限；逾時或失敗則顯示來源暫不可用。已有快照但系統成功取得時間超過 5 分鐘時，優先在最低間隔與預算允許下啟動一輪共用刷新，讓這次查詢短暫等待新快照；只有來源失敗、逾時或暫不可再呼叫時才回覆降級狀態。舊快照可留作內部恢復與時間參照，但不能把其中「有位」格位當作目前可用標記。
4. 「手動更新」與接近抵達時重新查詢都走同一個最低間隔和預算規則。按鈕不能保證每按一次都產生一次上游呼叫，也不能宣稱實際現場保留車位。
5. 各頁取得成功且通過 ID、筆數、缺值與重複檢查後，才原子地發布新快照；中途失敗不得把部分新頁面與舊頁面混成完整資料。若來源分頁期間自身更新，仍可能存在跨頁不一致，需量測或尋找來源版本／時間欄位。
6. TDX 按來源獨立設定點數、每分鐘速率與最大重試次數。免費帳戶每月 3 點，不能把新北市免費來源的候選刷新頻率套到 TDX。

`fresh` 僅表示在我們設定的擷取時效內且快照通過檢查；若來源未提供逐筆觀測時間，畫面應寫「系統於 HH:mm 取得」，不可寫「官方於 HH:mm 更新」。主系統應分別記錄刷新開始時間與**全部頁面驗證成功、快照發布的時間**，以後者作為 5 分鐘過期門檻的基準。建議另回傳 `source_observed_at`（可空）、`last_successful_fetch_at`、`last_attempt_at`、`freshness_state`、`quality_reason`、`refresh_in_progress`。有效的 0 位、未知、來源停用、過期均分開表示。

## 起始參數與可量測的驗收

Sponsor 選定 MVP **系統最近成功取得時間超過 5 分鐘即標示過期**，先試測，再依資料品質調整。這是「系統取得時間」門檻，不保證來源觀測也在 5 分鐘內。最低刷新間隔先以來源的 2／3 分鐘發布頻率作候選下限，不自動定為最終值；仍需量測不同間隔下的真實資料變化和 HTTP 請求數。高流量時可能需要放寬間隔；單純需求觸發原本可在無人使用時避免持續輪詢，後續已決定加入低頻定時取樣方向，詳見本文件末節。

Sprint 1 可驗收：

- 同一來源的多個並發查詢只產生一輪邏輯刷新；記錄該輪實際分頁與重試 HTTP 次數。
- 不完整或失敗的刷新不覆蓋上一份完整快照；首次無資料時顯示未知，不假裝 0 位。
- API 回應有取得時間與品質狀態；若無來源時間，UI 不冒稱官方更新時間。
- 記錄每來源每小時 HTTP 次數、成功率、刷新耗時、查詢等待時間、用戶可見快照年齡與過期回應比例。
- 實際刷新間隔、等待上限和過期門檻由上述量測及 Sponsor 的可接受資料年齡決定；未確認前保留設定項，不寫死為產品承諾。

單實例 MVP 可用應用程式鎖與 MySQL 保存快照／刷新紀錄；若部署多實例，需共享鎖，可評估 Redis。Redis 是協調與快取工具，不會讓政府來源更快更新。

## 2026-09-24 Sponsor 確認的首查與手動更新流程

- **首次無快照**：使用者完成地點搜尋後，主系統立即嘗試抓取新北市官方即時資料；按來源／資料集啟動一次共用擷取，不依每位使用者或每個目的地重抓。等待時間設上限，成功驗證完整資料後發布快照再顯示；逾時或失敗顯示「目前無即時車位資料」並可稍後重試，不把未知當 0 位。
- **手動重新整理**：先讀後端共用快照。若仍在可用時效內，直接回傳快照及系統取得時間；若已超過 5 分鐘，且來源已過最低刷新間隔、未有其他刷新、預算與來源可用，則啟動共用擷取，在等待上限內回傳新快照。尚不能抓取時，回傳舊快照及明確時效訊息；不得標示為最新。
- **擷取失敗或部分頁面失敗**：不發布半套新資料；保留上一份完整快照並標記更新失敗與最後成功取得時間。首次沒有任何完整快照則呈現未知。手動更新按鈕不繞過最低間隔、重試上限及共用鎖。
- **不同來源獨立狀態**：路邊刷新失敗不遮掉已可用的路外結果，反之亦然；畫面只列目的地圓形 300 公尺內實際收錄的汽車停車類型。

## 2026-09-24 過期查詢的刷新優先規則（Sponsor 關切，設計提案）

Sponsor 指出使用者要有效找到車位，不應在查詢時先看到超過 5 分鐘的舊「有位」結果。建議流程：

1. 查詢時檢查各來源最新完整快照。若在測試中的 5 分鐘時效內，顯示該快照及系統取得時間；若來源有可靠逐筆觀測時間，也需檢查觀測時間，不能只看剛下載成功。
2. 若超過 5 分鐘，先依來源最小間隔、共用鎖與呼叫預算啟動一次上游刷新；同時查詢共用這一輪，畫面顯示「正在更新」。等待上限內取得並驗證完整新快照，才顯示新的目前車位與可導航格位。等待上限需依實測擷取延遲設定。
3. 若官方失敗、逾時、仍在呼叫冷卻或新回應仍缺有效觀測，不把舊格位標為「目前有位」；保留地點／場站名稱和「目前車位無法確認」，舊數值如有必要只放在次要詳情並明確標最後取得時間，不能作為排序或導航推薦依據。
4. 若來源自己尚未發布新觀測，重新 HTTP 取得的資料也可能與上一輪相同；系統取得時間只能說明何時抓到，不能證明格位剛被觀測。來源觀測時間若缺失，需在品質說明保留此限制。
5. 抵達時預測與目前觀測分開：若模型經驗證可在目前觀測缺失／過期時仍可靠推論，可標為估計；否則顯示「預測資料不足」。不能把舊的目前空位數冒充抵達時答案。

此為待確認的 UX／等待策略，並非每位使用者都直接呼叫官方 API。實作前需量測主系統每來源的擷取耗時、來源實際變動間隔、刷新失敗率與 HTTP 請求量。

上述流程已定，具體等待秒數、來源最低間隔、刷新失敗冷卻時間及用量上限仍須按實際延遲與合併請求量設定。5 分鐘是畫面時效門檻，與是否允許向上游再抓一次分開判斷。

## 待決事項

1. 已選 5 分鐘作為初始過期門檻；超過時應先等待一輪刷新多久、何時先回舊資料？來源逐筆時間若早於系統取得時間很多，是否另設門檻？
2. 主系統採純需求觸發，還是少量預熱排程以降低第一位使用者的等待？

4. 是否需要對新北市平台提出高頻介接需求，並量測整檔與分頁方案的負載。

## 2026-09-24 請求量與刷新策略補充（提案）

新北市開發指引對公有路外停車場的「大量及高頻率」介接要求聯繫平台，但未公布數值門檻。主系統須依自己的實際請求量判斷瞬間速率、每日／每月總量、回應流量、錯誤與重試。獨立訓練收集器對同一外部平台的流量可另在營運層面彙總，詳見 `training-collector-operations.md`；它不參與主系統刷新決策。

Sprint 1 建議先採主系統「需求觸發的共用刷新」：依來源設最低刷新間隔；同時間多個使用者共用一輪結果；沒有使用者時不由主系統持續輪詢。此為設計提案，尚未選定 2 或 3 分鐘等實際間隔。靜態停車場清單另設較長週期，不隨每次動態刷新重抓。當沒有快照或來源失敗時，顯示未知／過期；5 分鐘是顯示門檻，不代表每 5 分鐘固定呼叫上游。主系統的首查等待時間與資料年齡須實測，再決定是否需要少量預熱。

主系統介接前須以自己選定的端點與抓取方式量測每來源實際 HTTP 次數、成功率、重試數、傳輸量與首查延遲；並核對新北市平台對預計上游用量的介接要求。面試展示以主系統實際監測解釋刷新頻率與成本取捨，不以訓練程式的排程或容量估算代替。

2026-09-24 的官方端點查核、HTTPS 探測限制及單輪可重做的量測步驟見 `realtime-source-measurement.md`；目前沒有成功的主系統 API 實測數字，上述間隔與等待值仍是候選。

## 2026-09-24 主系統刷新狀態機與量測計畫（本輪提案）

刷新單位先定為**來源資料集**，不是使用者、目的地或 300 公尺圓。路邊與路外各有啟用快照、成功取得時間、上次嘗試時間、下次允許時間、執行中狀態、失敗次數及用量紀錄。路外靜態位置目錄另設較長更新週期。新北市官方頁分別標示路邊每 2 分鐘、路外每 3 分鐘更新；這是資料集頻率，不能用來保證逐格逐場的新鮮度。[路邊資料集](https://data.ntpc.gov.tw/datasets/54a507c4-c038-41b5-bf60-bbecb9d052c6)、[路外資料集](https://data.ntpc.gov.tw/datasets/e09b35a5-a738-48cc-b0f5-570b67ad9c78)。

| 查詢時情況 | 主系統動作 | 使用者看到 |
| --- | --- | --- |
| 有完整且未超過 5 分鐘試驗門檻的快照 | 直接讀共同快照，依目的地在本地篩選；不因每位使用者重抓官方 API | 目前觀測與「系統取得時間」；來源逐筆時間若缺失則不冒稱官方剛更新 |
| 無快照，或舊快照已超過 5 分鐘 | 若已過來源最低間隔、失敗冷卻且預算允許，啟動每來源唯一的一輪擷取；其他同時查詢加入同一輪 | ETA 與可信位置先出現；車位顯示更新中，新快照完整發布後自動補上 |
| 同來源正在擷取 | 加入既有工作，不另發官方請求 | 查詢各自保留進度；路邊／路外可獨立完成 |
| 來源失敗、超時、冷卻中或預算耗盡 | 記錄原因並設下次允許時間；不發布部分新資料，也不立即連續重抓 | 位置仍可保留，車位標示目前無法確認；舊「有位」不作目前推薦 |
| 使用者手動更新 | 重新評估同一份來源狀態和限制；有效快照直接回、執行中就加入、允許時才新抓 | 明確告知資料取得時間與是否真的開始更新；按鈕不等於強制官方抓取 |

**持續開啟結果頁的已定行為**：頁面可見且某來源完整快照跨過 5 分鐘試驗門檻時，前端對該來源自動嘗試一次受控刷新；隱藏頁面暫停自動刷新與輪詢。恢復可見時先只讀主系統最新狀態，再判斷是否需要請求刷新。後端以來源為單位檢查共用工作、最低間隔、冷卻與預算，冷卻或失敗不讓前端定時器形成連續重試；多人使用同一輪。此刷新只處理車位，不重算 Google ETA。實際間隔和用量仍待量測。

**候選起始設定與後續更新**：先前「無人使用時不做背景預熱」是節省上游呼叫的早期候選，已被 Sponsor 新增的「成功運行歷史供未來訓練」及「使用者服務優先、低頻定時取樣居次」方向修正；背景間隔與上限尚未定。顯示過期門檻先沿用 Sponsor 選定的 5 分鐘。來源最短間隔可先以 5 分鐘作可量測假設，但正式值要由主系統完整擷取時間、來源變動、頁數與官方負載要求決定；失敗後應有比正常間隔更保守的冷卻。前景等待上限約 10 秒仍是交互原型候選，不是整輪來源擷取保證；超過後繼續背景工作，前端只查主系統進度。重試僅針對可恢復錯誤並計入每次 HTTP 用量；次數、逾時及 429 處理在測量後定。這些數字均未定案。

同來源並發時，單一 Spring Boot 實例先用執行中工作協調；取得執行權後再核對 MySQL 的快照／冷卻狀態，避免競爭造成重複抓取。`source_state`、用量與冷卻持久保存在 MySQL；Redis 已納入第一版，負責短期查詢進度和經驗證結果快取，不讓快取 TTL 充當刷新規則。若未來部署多個應用實例，須另驗證跨實例鎖與工作完成通知，不能因已安裝 Redis 就宣稱完成。

最壞連續需求的請求量應以**邏輯輪次 × 每輪實際 HTTP 頁數（含重試）**計算。例如每來源每 5 分鐘最多一輪，連續 24 小時是每來源最多 288 輪／日；兩來源合計最多 576 輪／日，尚未乘上分頁與重試。每 3 分鐘最多一輪則兩來源合計最多 960 輪／日。這些只是無冷卻且持續有人查詢時的上界示意，不是實際用量或官方配額。由主系統記錄每小時／每日輪次、HTTP 次數、傳輸量、p50／p95 刷新時間、查詢等待、過期比例，再設定運作上限。

Sponsor 曾提議冷區 60 分鐘、熱區 5／3 分鐘。官方開發指引支援欄位篩選，但**特定停車端點**能否按行政區分頁取齊、路外是否只需少數 ID、以及篩選後是否真的減少上游流量，尚未驗證。[官方開發指引](https://data.ntpc.gov.tw/applications)。若實際擷取仍是全市，熱區與冷區只能影響本地查詢呈現，不能各自設定真正節省呼叫的上游頻率。3 分鐘熱門預熱若畫面仍以 5 分鐘作刷新觸發門檻，也需要額外背景觸發規則才會生效；不能只把最短間隔改成 3 分鐘就聲稱資料更即時。第一版先以來源級需求觸發共用刷新測量，再決定是否加預熱／分區策略。

## 2026-09-24 需求熱度分層刷新（Sponsor 提案，待驗證）

Sponsor 提議非熱門區域以 60 分鐘作為低頻背景刷新，熱門查詢區域改為 5 或 3 分鐘。方向可行，但須將「有人查詢時的取得策略」與「無人查詢時是否預熱」分開：若無用戶且沒有首查延遲目標，純需求觸發可把背景呼叫降至零；每 60 分鐘固定抓一次仍會發生無人使用的請求。60 分鐘前取得的快照在既定規則下必須顯示「過期」，不能稱為最新車位。

熱度應依官方來源可實際篩選的單位計算，而非只依畫面上的搜尋區域。新北市開發指引支援欄位 filter；主系統須自己驗證路邊能否按新莊行政區取得、路外動態能否有效依區域或一組場站 ID 批次查詢。未驗證前，不預設「熱門地區」能降低路外上游成本。

早期候選策略曾是平時不排程抓取主系統即時來源；有查詢才在過期後觸發共用刷新。這個「完全不取樣」部分已由下方雙觸發決策取代。持續有需求時以 5 分鐘最低間隔起步、評估 3 分鐘熱門刷新等數字仍只是待量測候選。首次無快照或快照已超過 5 分鐘時，應顯示載入／過期並受控刷新；低頻背景取樣若存在，也不保證永遠符合 5 分鐘的使用者顯示門檻。

熱度切換需設進入與退出條件、最短持續時間及上限，避免少數重複查詢或範圍邊界導致頻率震盪；多用戶共用同一來源快照與鎖。驗收量測包括首查等待、熱點查詢數、每來源資料年齡、過期比例、主系統 HTTP 次數與傳輸量。若同一官方平台另有離線訓練流量，營運層面另行核對總負載；主系統不依賴該流量作即時查詢。此節為討論提案，沒有定案或開始 coding。

## 2026-09-24 雙觸發與使用者服務優先（已定方向）

Sponsor 同意使用者需求觸發與低頻定時取樣共用主系統來源級擷取流程，並指定資料庫主要服務使用者，未來訓練用途居次。兩種觸發都讀同一啟用快照、受相同最低間隔、失敗冷卻、並發鎖與請求預算約束；正在執行的一輪可供使用者加入，不因背景取樣再開一輪。預算或系統負載不足時先略過背景取樣並記錄缺口，不讓訓練完整度要求拖慢使用者查詢。成功驗證發布的快照留歷史版本；大量匯出／離線訓練另行排程。定時間隔、每日來源 HTTP 上限、負載停用條件與記錄格式待量測，不能把本節當作保證固定取樣。

Sponsor 進一步同意**每來源分開計量並預留互動查詢可用量**：背景取樣只使用可用餘量，不能耗盡使用者刷新預算；一輪分頁及每次重試都計入實際 HTTP 用量。來源硬限制或冷卻始終優先於使用者要求，不能用「優先服務」作超額理由。新北市官方 API 與 TDX 另有各自規則，不能混用點數。來源不足時前端顯示阻擋原因及資料時間，舊有位不作即時推薦；具體保留量與上限仍待量測。
