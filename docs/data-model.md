# 主系統資料模型（Sprint 1 討論稿）

更新日期：2026-09-24。狀態：邏輯設計提案，尚未實作或建立資料表。用途是支援新莊汽車路邊格位／路外停車場的使用者即時查詢，並依 Sponsor 新要求累積可供未來離線訓練的主系統運行歷史。獨立 collector 目前有資料不完整問題而暫緩盤點；它不參與使用者即時查詢。日後只有經驗證的模型產物進入線上推論流程。ML 欄位語意以 `ml-source-contract.md` 為準。

## 先分清三種東西

1. **停車位置／目錄**：格位與停車場在哪裡、屬於哪一來源、是否確認適用一般汽車。位置不等於目前有空位。
2. **來源已發布觀測歷史與最新啟用版本**：官方每次成功取得並驗證通過的狀態按快照版本保存；路邊與路外各有自己的啟用版本和取得時間，不能把兩者合成一個「全站同步時間」。歷史版本供未來離線訓練篩選，啟用版本供即時查詢。
3. **抵達時預測**：針對一次使用者行程的 ETA 計算。與觀測分開回應，第一版不預設長期保存每位使用者的行程與預測。

## 建議的邏輯資料集合

| 資料集合 | 最少保留的語意 | 注意 |
| --- | --- | --- |
| `parking_place` | 內部 ID、`on_street_spot`／`off_street_lot` 類型、顯示名稱或格位識別、WGS84 座標、車種／格種適用性與規則版本、目錄來源與核對狀態 | 路邊「目的地 300 公尺內至少一格」是每次查詢計算的範圍摘要，不是一座永久停車場；未核實車種不得標可停。目錄更新與資格規則詳見 `parking-catalog-design.md`。 |
| `source_mapping` | 資料集、來源原始 ID、內部停車位置 ID、對應狀態／版本 | 同名不代表同一場；TDX 與新北市 ID 核對前不合併。 |
| `ingestion_run` | 資料集、開始／結束、成功／失敗、頁數、實際 HTTP 次數、錯誤與取得時間 | 支援上游用量和品質說明；失敗紀錄不得覆蓋前一份完整快照。 |
| `availability_snapshot` | 快照 ID、資料集、完整驗證通過的時間、筆數、版本／品質狀態 | 路邊與路外各自有一份目前啟用的快照；成功發布的舊版本保留為可追溯歷史，保留期限／歸檔待量測。來源逐筆觀測時間另存，不能將「取得」寫成「官方更新」。 |
| `availability_observation` | 所屬快照、來源 ID／內部 ID、原始值、可空的標準化剩餘數或格位狀態、可空來源觀測時間、異常原因、映射／規則版本 | 觀測隨已發布快照保留，不能只覆寫最新列；有效 `0`、沒有數值、過期、來源停用分開。過期依快照／觀測時間判斷，不改寫歷史原值。 |
| `source_state` | 每資料集目前啟用的快照 ID、上次嘗試／成功取得時間、下次允許擷取時間與用量上限狀態 | 重啟後仍遵守呼叫冷卻；應用內的執行鎖只在單一實例有效。 |

以上是多來源共用的邏輯集合：`availability_observation` 是統一動態觀測表，搭配位置目錄與來源 ID 對應；每個來源由自己的 adapter 轉成共同欄位，前端不接觸來源專有格式。細節見 `backend-stack-and-normalization.md`。實際資料表是否合併及索引待查詢量與來源欄位確認。MySQL／JPA 可先用於目錄、來源狀態與快照中繼資料；大量觀測列是否採 JPA 批次寫入，須量測，不先假設每列單獨儲存也能達到刷新延遲目標。

## 運行歷史與未來離線訓練（Sponsor 已指定方向）

成功發布的新快照採新增版本而非原地覆寫。線上查詢只讀每來源的啟用版本；離線訓練日後從合格歷史版本按時間匯出，並保留來源、原值、標準化規則與品質原因。失敗輪次仍可記在 `ingestion_run`，但未發布候選、缺失值、模型補值和 Redis 快取不作真實訓練標籤。資料庫的歷史保存與訓練工作解耦，避免訓練查詢影響使用者查詢。

主系統按使用者需求才觸發刷新時，歷史時間點不均勻，且較多人查詢的時段可能取樣較密。這些觀測可作後續素材，仍須檢查缺口與取樣偏差；若訓練需固定間隔，是否增設受預算控制的收集排程另行決定。MySQL 長期儲存量、索引、保留／歸檔與匯出格式待量測；不能因 Sponsor 要求未來可訓練，就預設無限期保存每輪全量資料。

Sponsor 已決定主資料庫優先服務使用者，訓練用途居次。主系統可由使用者需求與低頻定時取樣共用同一擷取／驗證／發布流程；定時取樣在來源或系統預算不足時可略過，並在歷史品質中留下缺口。大量離線匯出與訓練不在使用者請求中執行；實際隔離方式與保存量待量測。

## 完整快照發布規則

1. 依資料集啟動一筆擷取執行紀錄；在新的候選快照下抓取所有分頁。
2. 驗證頁面成功、ID／重複／筆數與必要欄位；失敗便標示此輪失敗，維持前一份啟用快照。
3. 全部通過後，才以單一交易把此資料集的 `active_snapshot_id` 指向新版本，並記錄成功取得時間。
4. 一次使用者查詢先固定路邊和路外各自的啟用版本，再讀取該版本的觀測；兩種來源可以有不同版本與時間，但同一來源不能混入上一版的一部分資料。

例如路邊第 1、2 頁成功而第 3 頁失敗時，不發布「兩頁新資料＋一頁舊資料」。若上版已超過 5 分鐘，仍保留供恢復與位置參照，但畫面標示目前車位無法確認，不能把舊空格當最新推薦。這也適用於 Spring Boot 容器在擷取途中重啟。

整輪與逐筆的品質判斷、異常隔離和驗收情境詳見 `snapshot-validation.md`；少量個別未知列可隨完整來源快照發布，但路邊範圍預測仍須另外驗證該範圍覆蓋率。

## 目的地附近查詢與預測

- 目錄先用包住 300 公尺圓的經緯度矩形取候選，再用 WGS84 座標核算直線距離是否小於或等於 300 公尺；矩形角落不得誤納入。新莊邊界未收鄰區時標示覆蓋不完整。實際索引與查詢時間待測量，詳見 `nearby-search.md`。
- 路邊區域結果由該次 300 公尺內**已核實適用汽車**且品質達標的格位觀測彙整；路外結果保留每一場的剩餘位與品質。模型輸出的機率附目標時間、模型版本及可靠性，不回寫官方觀測。
- 覆蓋率不足、格位資格未核實、來源狀態碼未確定或模型不適用時，不輸出虛構機率。`null` 不等於 `0`。

## 待驗證

- 新北市路邊與路外實際來源 ID／位置對應、格位車種與狀態碼、來源是否提供逐筆觀測時間。
- 每輪分頁筆數與寫入延遲、MySQL 附近查詢時間、候選快照保留期與清理、備份／還原；Docker 遠端環境需要驗證重啟後仍只顯示通過完整驗證的快照。
- 多實例若成為交付要求，須把執行中刷新協調與短期查詢進度改為跨實例可共享；單一實例方案不假裝已支持多實例。
