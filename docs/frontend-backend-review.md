# 前後端架構盤點（Sprint 1）

更新日期：2026-09-24。這是設計盤點，主系統尚未 coding。進度圖見 `project-status.html`。

## 結論

- **前端產品需求足以開始後端契約設計**：搜尋／起點／ETA、300 公尺結果、電腦版地圖優先與手機版上地圖下清單、過期資料先受控刷新、格位小卡外部路線及主要狀態已有方向。前端技術、地圖供應者、Google 搜尋接法、實際面板尺寸、標記密度及行動裝置原型仍未定案；這些需要在實作前收斂，但不阻止先定回應語意。
- **後端方向可行但尚未定案**：Spring Boot 模組化單體、MySQL／JPA、獨立訓練 collector、主系統受控共用刷新已有方向；已開始 `backend-contract-proposal.md` 的請求／回應語意討論。API 正式契約、地理查詢、快照一致性、服務上限、模型推論介面及金鑰界線仍需設計。
- **資料與 ML 是兩邊共同依賴**：路邊格位資格、狀態碼、路外有效剩餘位、來源時間與訓練標籤未核實前，不能把「有位」或機率視為可靠結果。

## 前端待定的契約

1. 地點搜尋：候選包含地址／地標／店名，體驗以類似 Google Maps 為目標；如何顯示同名不同地點、無結果、服務失敗與新莊區外？Google Places 是否為正式供應者，前端用何種技術？
2. 起點與時間：定位許可／拒絕、手動起點、當下預填、未來出發日期與時區；Google ETA 過期或失敗時畫面如何保留停車結果？
3. 查詢結果：地圖與清單已決定同頁同時顯示；路邊區域主要機率、目前有位格位位置次要明細、路外每場機率應如何連動？資料來源時間、系統取得時間、模型時間各放在哪裡？
4. 狀態與操作：0 位、未知、資料超過 5 分鐘、更新中、刷新失敗、預測不足、無收錄、路邊／路外部分失敗；重新整理如何顯示「已使用最新快照」或「正在向來源更新」？
5. 介面驗收：手機和桌面最小可用範圍、鍵盤操作與文字可讀性、地圖標記量與清單排序規則；先用原型驗證 5 分鐘時效文案。

## 後端待定的契約

1. 查詢 API：輸入目的地與起點選定後的座標、出發時間；輸出目的地 ETA、300 公尺類型化結果、目前觀測、抵達時預測及其各自品質狀態。Google 地點搜尋與路線計算要與停車資料刷新分開計量。
2. 停車目錄與地理查詢：來源 ID、共同座標系統、汽車適用性、路邊格位／路外場站資料表，以及直線 300 公尺的索引與查詢效能。
3. 刷新與資料一致性：按來源資料集而非按使用者刷新；首次無快照觸發一輪擷取，多人共用結果；各頁完整驗證後原子發布新快照。設定首查等待上限、最低間隔、失敗冷卻、重試和每來源預算。
4. 資料時效：區分來源觀測時間、快照成功發布時間、查詢時間；有效 0、未知、過期及負值狀態不可混淆。路邊與路外各自降級。
5. 模型推論：離線訓練產物如何版本化、由 Spring Boot 讀取或經獨立推論程序取得、模型失敗時如何降級、推論用到哪些查詢當下可取得的特徵。必須避免訓練與推論欄位不一致及未來資訊洩漏。
6. 本機展示與安全：Docker／環境變數如何重現；Google 憑證限制、政府 API 呼叫紀錄、官方來源與 collector 的合併用量監測。Redis 導入須由多實例或實測瓶頸支持。

## 推薦的決策順序

先確認來源欄位與兩類預測標籤，再定 API 輸入輸出和畫面草圖；接著實測一次官方擷取的耗時／頁數，才能設定首查等待上限和刷新間隔。前端框架與地圖供應者可在完成一頁草圖及 Google 用量估算後選擇，無須先擴大服務架構。
