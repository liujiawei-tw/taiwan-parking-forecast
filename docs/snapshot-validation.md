# 即時快照驗證與發布（Sprint 1 討論稿）

更新日期：2026-09-24。狀態：Sponsor 已決定缺頁／無法確認取齊時不發布、少數個別壞值可按品質狀態保留；具體比例門檻仍須由主系統對新北市來源的實測決定，尚未實作。本規格只定主系統向官方 API 取得用戶即時資料後的驗證與發布；獨立訓練資料收集器不參與。

## 「完整」的意思

路邊格位、路外停車場動態各自擷取與發布。主系統稱一份快照「可發布」，是指**本系統在同一輪抓取中取得預期全部頁面，辨識得出目標資料，並把無法判讀的個別觀測標為未知**。這不表示政府來源在多頁抓取期間完全不變，也不表示每一格／每一場都剛被感測。來源若無版本號或觀測時間，這個限制必須保留。

## 三層檢查

| 層次 | 檢查 | 不通過時 |
| --- | --- | --- |
| 整輪取得 | 每頁 HTTP／JSON 成功、分頁正常結束、未超過頁數上限；新莊試點先排除意外空集合 | 整輪失敗，不切換啟用快照；保留上一份完整快照及其取得時間。 |
| 實體與覆蓋 | 路邊格位來源 ID／行政區／位置可識別；路外動態以已核對的新莊靜態場站 ID 關聯；檢查缺 ID、同目標 ID 重複／衝突、與前次完整快照的覆蓋差異 | 有問題的實體隔離並計入覆蓋缺口；若資料集大量縮水或無法判斷主要目標，整輪不發布。嚴重門檻按實測設定，不能把舊有 2,124 格／149 場永久寫成固定值。 |
| 個別車位值 | 保留原始狀態／數量；核對車種、碼表、負值、缺值、車位數與容量的矛盾、逐筆來源時間 | 個別列標 `unknown`／`invalid` 並記原因；有效 `0` 照實保留。來源 `-9` 等已知無即時值不能轉成 0。若有效覆蓋不足，路邊區域預測或相關場站預測不輸出。 |

路外動態來源目前抓取全市、再以新莊靜態 ID 關聯；全市其他區域的重複 ID 不直接視為新莊快照失敗。新莊目標 ID 若有互相衝突的重複列，該場的狀態先標未知，並計入覆蓋率，不任選一筆。路邊格位狀態碼在官方語意核實前，可以保存原值，但不可向使用者發布「目前可停」判斷。

## 發布與畫面

候選快照和擷取紀錄先寫入；驗證通過後，才用一次資料庫交易切換**該資料集**的啟用快照 ID。路邊與路外可以各自成功或失敗，畫面分別顯示結果和取得時間。若本輪失敗，上一份完整快照不改寫；若已超過 5 分鐘測試門檻，畫面顯示「目前車位無法確認」，舊「有位」不作導航推薦。

對已通過整輪檢查但有少量未知列的快照，可發布**有效部分加明確覆蓋率／未知原因**；不把未知列當已滿。路邊「300 公尺內至少一格」預測還需查詢範圍內的有效格位比例與模型可用條件；整個資料集可發布，不代表任意 300 公尺範圍都能做可靠預測。

上述「缺頁不發布、少數逐筆壞值可標未知」已由 Sponsor 確認；可容許多少無效列、異常縮水時是否拒絕整輪，仍待實際回應分布量測。原始無效值及原因須可追溯，不能靜默刪列後宣稱 100% 覆蓋。

## 驗收情境

1. 第三頁 HTTP 失敗：本輪不發布；保留上一份完整版本，記錄失敗頁與上游請求數。
2. 來源回報汽車剩餘 `0`：在欄位語意與場站 ID 有效時發布 `0`，UI 顯示「目前 0 位」。
3. 來源回報 `-9`、缺值或未知格位碼：原值保留，該實體狀態未知；UI 不顯示「0 位」或「目前有位」。
4. 少數列缺 ID／位置或新莊場站重複衝突：隔離並計算覆蓋；未達實測後設定的最低品質時不發布，不能悄悄刪掉大量實體。
5. 路邊成功、路外失敗：路邊啟用新快照；路外仍保持舊版本與失敗／過期狀態，不能共用同一取得時間。
6. Spring Boot 容器在候選快照尚未發布時重啟：啟用版本不變；未完成候選可在背景清理，使用者不會讀到半套資料。
7. 抓取成功但來源提供的觀測時間很舊：記錄系統取得時間與來源觀測時間兩者，標示來源資料較舊；不能因本系統剛下載就稱資料剛更新。

## 快照發布交易流程草案

第一版採「候選快照寫入」與「啟用快照切換」分離，避免使用者讀到半套資料。路邊與路外各自是一個資料集，各自擷取、驗證、發布與過期；其中一類成功不代表另一類也成功。

建議流程：

1. 建立 `ingestion_run`，狀態為 `RUNNING`，記錄來源、觸發方式與開始時間。
2. 從官方來源擷取資料，計算 HTTP 次數、分頁結果、筆數與錯誤。
3. 建立 `availability_snapshot`，狀態為 `CANDIDATE`。
4. 將候選觀測寫入 `availability_observation`，每列保留來源 ID、系統內位置 ID、原始狀態值、標準化狀態、品質狀態與時間。
5. 執行整輪品質檢查：分頁是否完整、主要目標 ID 是否可識別、重複／衝突是否超出門檻、逐筆壞值比例是否可接受。
6. 若整輪不通過，將 `availability_snapshot.snapshot_status` 改為 `REJECTED`，`ingestion_run.run_status` 改為 `REJECTED` 或 `FAILED`，更新 `source_state` 的失敗原因、冷卻與下一次可刷新時間；不改 `active_snapshot_id`，不更新 Redis 快取。
7. 若整輪通過，開啟短交易，將候選快照改為 `PUBLISHED`，更新 `published_at`，並把 `source_state.active_snapshot_id` 切到新快照，同時更新最後成功取得時間、來源觀測時間與下一次可刷新時間。
8. 交易提交後，才失效或更新 Redis 中對應來源的快取與查詢進度；Redis 更新失敗不應回滾已發布的 MySQL 快照，但必須記錄並讓後續讀取可從 MySQL 重建快取。

交易邊界的原則是：大量觀測寫入可以發生在候選階段；啟用版本切換要短、明確且可回復。使用者查詢只能讀 `source_state.active_snapshot_id` 指到的已發布快照，不掃描最新候選快照。

失敗處理：

- 官方來源抓取失敗：不建立可發布快照；上一份已發布快照維持原狀。
- 部分分頁成功但缺頁：候選快照拒絕；不讓使用者看到半套資料。
- 少數逐筆壞值：可保留壞值原始碼並標未知，是否發布取決於品質門檻。
- 發布交易前 Spring Boot 重啟：候選快照仍是 `CANDIDATE`，啟用版本不變；啟動後可清理或標記為中斷。
- 發布交易後 Redis 更新失敗：MySQL 仍是事實來源；後續讀取或排程可重新補快取。

這個流程同時支援使用者即時查詢與未來模型訓練：查詢只讀已發布版本；訓練匯出可讀已發布觀測歷史並使用快照品質欄位過濾。未發布候選、失敗擷取和模型補值不能當成訓練標籤。
## 待量測／待確認

- 分頁是否有官方總筆數或版本訊號；若沒有，多頁之間來源更新可能造成重複或漏列，只能量測並對外標示此限制。
- 各來源正常筆數波動、重複／缺值比例、Xinzhuang 靜態 ID 對應覆蓋、每輪擷取與 MySQL 寫入的 p50／p95；依此訂可發布的最低覆蓋門檻與異常警示。
- 新北市路邊 `parkingstatus`／`cellstatus` 官方碼表與一般汽車適用性、路外 `AVAILABLECAR` 實際欄位及特殊負值。未核實前保留原始值，不憑猜測提供有位判斷。
