# Sprint 0：等待新北市長區間資料時的工作清單

更新日期：2026-09-23。新北市路邊格位 2024-04-01 至 2026-07-31 的歷史資料已申請、仍待 TDX 產製。本清單是待 Sponsor 排序的一人 Scrum backlog；完成前不視為已實作。

## 先做：不需新資料與額外點數

1. **定義兩個預測問題與驗收條件**（產品／資料，約半天）：路邊以「指定格位在到達時是否可停」為候選；路外以「指定停車場於到達時是否仍有汽車車位」為候選。決定使用者輸入的是預計抵達時間還是行車分鐘數、試點地點和 10／30／60 分鐘中先支援哪些。交付：更新 `requirements.md`，每項有可檢查的輸入、輸出與資料不足情境。Sponsor 負責產品取捨，AI 協助撰寫與面試審查。
2. **確認官方欄位與統一資料契約**（資料工程／架構，約半天至一天）：用 TDX Swagger／資料字典核對新北市 `SpotStatus`、`ServiceStatus`、`DeviceStatus`，以及桃園機場 `SpaceType`、`ParkingAreaID`、`FullStatus`；記錄來源欄位、單位、時間區、主鍵、可空值和對應的內部欄位。路邊格位、路外停車場分開保存來源語意，在查詢輸出層提供共同的名稱、位置、資料時間與狀態。交付：可審查的欄位對照表；不認得的狀態碼明確標「待確認」。
3. **完成現有資料品質檢查設計**（資料工程，約一天）：新北市單日資料先檢查每格位同時間重複、觀測間隔、缺口及原始列未排序的影響；桃園機場檢查同一停車場／車種／分區重複及各場滿位事件。交付：品質報告的檢查項目、公式與通過／警示規則。若要執行大量資料分析，另開實作工作，不在本文件暗示已完成。
4. **定義評估與防資料洩漏規則**（ML／面試審查，約半天）：路邊評估有位機率的校準及「預測有位、到場無位」比例；路外評估有位判斷與剩餘位數誤差。基準至少含「維持目前狀態」與「相同時段歷史比例／中位數」。所有特徵只能使用預測當時已知資料；長區間資料到齊後按時間切訓練、驗證、測試，不隨機混洗。交付：評估表與資料切分草案；單日資料不宣稱跨日效果。
5. **列出即時資料所需端點與擷取預算**（架構／營運，約一天）：只讀官方 Swagger 與既有文件，列出場域基本資料、路邊格位或路段狀態、路外剩餘位、來源更新時間、是否可按範圍取得；區分靜態與動態資料。先按官方費率估算，未實測的回應大小留空；不得把使用者每次搜尋轉成一次 TDX 呼叫。交付：端點候選與月度預算表，後續經 Sponsor 同意再做小規模實測。

## 資料產製完成後

1. 記錄申請頁的預估與實扣點數、檔案大小、日期、分檔數及 MD5；確認會員剩餘點數。
2. 保留原始 ZIP／CSV，只在專用原始資料夾落地；檢查實際日期覆蓋、缺日、欄位版本與 2026-08-09 樣本是否一致。
3. 先抽取可控制的格位或路段做跨日品質檢查，再定最終訓練／驗證／測試區間；不因檔案很大就直接整包載入 Notebook 記憶體。
