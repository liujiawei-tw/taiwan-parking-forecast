# 需求與驗收條件

更新日期：2026-09-24。狀態：Sprint 1 需求整理；目的地搜尋形式正在細化，其餘優先順序仍待確認。

## 使用者需求

### R1 查詢目的地附近的停車選項

使用者輸入目的地關鍵字後，系統提供可辨識的候選地點；使用者選定地點後，以其座標查詢目的地周圍直線距離 300 公尺圓形範圍內、TDX 或已核對的地方政府來源收錄的停車選項。候選地點預期涵蓋地址、地標及店名，搜尋體驗以類似 Google Maps 的候選選取方式為目標。搜尋後同一頁同時顯示地圖與結果清單；路邊格位與路外停車場按實際收錄情況呈現，只有一種類型時只顯示該類型。每筆顯示名稱、類型、位置、來源及資料時間。若該地區沒有可用即時資料，明確顯示原因，而不是回傳空白或暗示都有車位。

**目的地搜尋驗收（草案）**：輸入時可見可辨識的候選地點並由使用者選定；同名結果須能辨識地址／行政區。無結果、搜尋服務失敗或座標超出新莊 MVP 範圍時給明確訊息，不任意選第一筆或顯示沒有停車位。選定後，後續重整車位資料沿用座標，不重做地點搜尋；來源座標系統轉為共同坐標系統後才進行距離篩選。候選搜尋請求節流、服務供應者、費率、快取與顯示條款待選型。

**試點外與跨界驗收（已決定的產品行為）**：若已選目的地位於新莊 MVP 支援範圍外，保留該地點並顯示「目前尚未支援此地區」及改搜入口；此次查詢不呼叫 Google Routes ETA 或官方車位來源，不以空清單宣稱附近沒有車位。若目的地在新莊內，但 300 公尺圓跨出已收錄範圍，仍計算 ETA、呈現已收錄選項並標示部分覆蓋。此時不輸出代表**完整 300 公尺圓**的路邊抵達時機率；已收錄且通過資料／模型驗證的路外停車場可各自顯示單場抵達時機率，並提示附近清單可能不完整。未收錄區域不得視為 0 位。

**覆蓋未知驗收（已決定的產品行為）**：若無可靠依據判定整個 300 公尺圓是否都被路邊資料收錄，保留已核實位置，但路邊完整範圍的抵達時機率顯示「覆蓋範圍未確認，暫無法預測完整範圍」。合格路外場站的單場預測可獨立顯示；此時仍須另外標示附近場站清單的覆蓋情況。地理覆蓋、目錄完整性、目前車位觀測與模型可預測性不能混為同一狀態。

**地圖與清單驗收（草案）**：搜尋完成後兩者在同一頁可見；清單項目能辨識地圖上的對應位置，路邊區域預測與目前有位格位明細不得混為同一狀態。手機與桌面布局、標記密度、選取連動、底圖及實際 Google 服務選型仍待設計。

### R2 區分觀測、估計與未知

有即時車位時顯示來源回報的剩餘數及可確認的時間語意：來源觀測時間與主系統成功取得時間不能混稱。若資料缺值、超過系統成功取得後 5 分鐘或來源失敗，顯示不同狀態；5 分鐘是先測門檻。模型補值只能標為「估計」，並顯示可信程度；不能顯示成官方即時數值。

**過期數值驗收（已決定）**：有效 0 位須回數字 0；未知或過期時，主要 API 的「目前可用數」為空值，並分別回未知或過期狀態及原因。過期前的數值若供參考，只能在次要資訊中附原資料時間，不得標為目前有位或用來推薦格位路線。來源若提供可信觀測時間，系統重新取得舊觀測不會把它當成新的來源觀測。

### R3 抵達時預測

預計抵達時間由 Google 路線服務依出發點、選定目的地與駕車路線估算，不要求使用者自行輸入。出發點同時支援裝置目前位置與使用者手動搜尋選取的出發地；出發時間預填當下，使用者也可手動改成預計出發的日期與時間；Google 估算到搜尋目的地的抵達時刻。預填當下不會自動開導航，只有使用者明確選擇開始導航時才開啟外部 Google Maps 或 Apple 地圖。主系統不提供內建導航，也不要求逐一計算到每個停車選項的 ETA。拒絕定位時仍可改用手動出發地。若定位或路線服務失敗，顯示無法計算 ETA，不能自行填入固定分鐘數冒充路線估計。

**ETA 呼叫驗收（已決定）**：選定起點、目的地和出發時間後，使用者送出行程規劃才請求 Google ETA。修改條件後須明確重新規劃；輪詢進度、持續可見頁面的車位自動刷新和手動「更新車位」不呼叫 Routes。Google 地點搜尋、Routes ETA 和政府車位來源分開記錄用量與內部上限。Routes 失敗或額度阻擋時保留有效目前車位，抵達時預測標示缺 ETA，不用舊 ETA 冒充新規劃。

**預測目標時刻驗收（已決定）**：路邊與路外抵達時機率均針對本次 Google ETA 對應的實際目標時刻；後端不得自行代入固定 60 分鐘或 10／30／60 分鐘時點來充當 ETA。模型若無法可靠支援該時刻，仍顯示 Google ETA 與可用的目前車位，機率欄位顯示「預測資料不足」及原因，不修改 ETA 或填入虛構機率。

第一版以新莊區的汽車停車資料作路邊與路外試點；機車暫不納入。路邊主要顯示「抵達時，目的地座標方圓 300 公尺內至少有一個適用格位可停」的預測機率；次要明細列出目前來源回報有位、且已確認適用汽車的格位位置，明細不代表抵達時仍有位。路外對範圍內每座收錄停車場顯示抵達時有汽車位的預測，剩餘數預測可作附加結果。兩類預測能力都屬 20 天目標，但單一目的地只顯示實際收錄的類型。兩者共用時間與資料品質框架，各自核對標籤並按時間切分回測。資料不足時顯示「預測資料不足」，不編造機率。預測結果附模型版本與產生時間。最低有效觀測比例仍待確認；新莊邊界未收鄰區時標示覆蓋不完整。

**過期觀測與預測驗收（已決定）**：若當次使用的模型需要最近車位觀測，而該觀測過期且受控刷新仍未取得有效新資料，該類抵達時預測顯示「預測資料不足」及原因，不輸出機率；目前車位狀態則獨立顯示過期／無法確認。日後只有經時間切分回測、確定不需目前觀測的模型，才可在明確標示模型依據與版本下作歷史規律估算。路邊與路外獨立判斷。

**格位外部路線驗收（草案）**：只有當目前來源回報有位、已確認為一般汽車可停、格位座標可信且資料在可接受時效內時，標記小資訊卡可標「目前有位」並提供「查看路線」。按鈕把該格位座標交給外部地圖作駕車路線；卡片顯示系統取得時間，不能保證抵達時仍有位或車位已保留。過期、未知或資格未核實時不得沿用「目前有位」文案；中性路線入口是否保留待決。

### R4 TDX 額度控制

一般使用者查詢不直接呼叫 TDX。排程擷取設有可設定的頻率、呼叫預算、失敗重試限制、資料過期規則和使用量監測。當額度接近上限時，服務降級仍可顯示最後可用資料及其時間。

### R5 多來源統一契約（第一版建立基礎，後續擴來源）

第一版即讓新北市路邊與路外資料先經來源轉換器，成為主系統一致的位置、來源 ID、汽車剩餘位／格位狀態、時間及品質欄位，再由 API 回前端；不能讓 Vue 依來源格式逐一判讀。後續新增 TDX、地方政府或業者時沿用同一契約，保留來源及原始 ID；同一停車場經核對後才合併，欄位衝突須有可追溯的選用規則，不直接覆蓋原始觀測。見 `backend-stack-and-normalization.md`。

### R6 首次查詢與重新整理

首次查詢沒有任何可用快照時，後端應啟動一次共用的新北市即時資料擷取；畫面先顯示目的地、300 公尺範圍，以及已完成的 ETA 與已收錄且位置可信的停車選項，車位標示「更新中」。沒有可用停車目錄時不捏造格位位置。前端向主系統查詢同一輪刷新進度；完整快照驗證成功後自動補上車位與可用預測，進度查詢不重複呼叫政府 API 或 Google ETA。一般查詢或手動重新整理都先檢查後端快照；快照仍有效就回傳其取得時間，超過 5 分鐘且符合來源最低間隔、預算與共用鎖規則時，應優先啟動一次共用擷取。結果頁持續可見且資料跨過 5 分鐘時，也對過期來源自動嘗試一次受控共用刷新；頁面隱藏時停止自動刷新，返回可見時先只讀最新狀態再決定是否請求刷新。冷卻、預算阻擋或失敗時不自動密集重試；多人查詢共用同一來源輪次。失敗、逾時或暫不能再呼叫時，保留上次完整快照供系統恢復，畫面標示目前狀態無法確認；舊「有位」格位不可繼續作為目前可停標記或導航推薦。首次失敗則顯示目前無即時資料，不顯示 0 位。路邊與路外各自顯示取得及失敗狀態；重新整理不保證每按一次就呼叫官方 API，也不重算 Google ETA。具體等待與輪詢上限、來源間隔待實測。

### R7 Docker 與遠端可部署性

主系統須以 Docker 映像及可重現的部署設定在另一台伺服器啟動，包含 Vue 正式建置頁面、Spring Boot API、MySQL 資料持久化與 Redis 短期狀態／快取。本機資料路徑與開發機常駐程序不得是遠端運行的必要條件。資料庫密碼、TDX／Google 憑證不得寫入映像或 repository。遠端透過瀏覽器使用裝置目前位置時，網站須以安全環境（通常為 HTTPS）提供。Docker 交付屬必要範圍；實際遠端上線時點與主機資訊待 Sponsor 提供。

### R8 運行歷史可供未來模型訓練

主系統每次成功發布的官方即時資料快照，除供目前查詢外，也要在 MySQL 留下可追溯的標準化歷史觀測；不能只覆寫最新值。歷史保留原始來源值與轉換後值、ID 對應與版本、品質／缺值原因、來源觀測時間與系統取得時間。未來可依時間匯出合格觀測供離線訓練與回測；失敗或未發布的候選快照、Redis 快取與模型預測不可充當真實答案。保存期限、容量／歸檔、來源授權及是否補充定時取樣待量測決定。按使用者需求觸發的刷新會造成不規則時間間隔，不能保證單靠這批歷史就足以完成兩類模型。

**優先順序（已決定）**：MySQL 與官方來源擷取首先服務使用者目前查詢；歷史留存與模型訓練為次要用途。主系統可用同一受控流程接受使用者需求觸發及低頻定時取樣，但背景取樣須受來源預算、共用刷新與系統負載限制；不足時可略過並記錄缺口。離線訓練／大量匯出不得阻塞使用者查詢。低頻實際間隔和上限待主系統量測，不先承諾固定訓練資料量。

**來源預算驗收（已決定的原則）**：每個官方資料來源分別計量實際 HTTP 請求與重試；為互動查詢保留可用呼叫量，低頻背景取樣僅用餘量，不能先耗盡來源預算。互動查詢仍受來源硬限制與失敗冷卻約束；額度不足時回明確原因與最後成功取得時間，不承諾能強制抓新資料。保留量和上限須依各來源實際規則及每輪頁數量測訂定，不能把 TDX 點數直接套用於新北市 API。

## 品質與驗證

- 保存資料來源、來源更新時間與系統取得時間；保留足夠歷史供回測。
- 以時間順序切分資料回測，避免使用預測當時尚不存在的資料。
- 監測「預測有位、實際無位」比例、資料過期率、縣市覆蓋率與每月 TDX 點數消耗。
- TDX 認證資訊不得提交至 Git；部署與本機設定方式需可重現。
