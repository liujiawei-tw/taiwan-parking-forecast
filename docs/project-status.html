停車預測專案｜進度與待辦

新莊區 MVP：搜尋目的地、計算抵達時間，顯示目的地方圓 300 公尺內收錄的汽車停車選項，以及抵達時有位的預測。

進度判讀：「已決定」表示需求／方案已確認，不表示程式已完成。目前主系統的前端、後端與兩類預測均尚未實作；訓練 collector 雖有排程，Sponsor 回報匯出資料不完整，相關盤點與模型驗證暫緩。

各工作線：已確定與未完成

前端：Vue 3＋Vite 已定，尚未實作

搜尋與結果畫面

  • 已定：Google Maps JavaScript 地圖與 Places API (New) 搜尋、起點兩種方式、出發時間、300 公尺結果；電腦版地圖優先、固定區域摘要與「查看全部結果」，手機版上地圖／下清單。路邊格位小卡提供資料時間及外部「查看路線」。
  • 待定：格位資格與座標驗證、Google 實際用量、面板尺寸、無障礙操作。
  • 待定：載入中、0 位、無資料、過期、ETA 失敗及預測不足的完整互動原型。
後端：Spring Boot Web、MySQL、Redis 已定，契約待細化

即時查詢與儲存

  • 已定：Spring Boot Web／Spring MVC REST 模組化單體；MySQL／JPA 保存啟用快照與可追溯歷史，供未來離線訓練；Redis 保存短期查詢進度及經驗證結果快取。使用者查詢優先，低頻定時取樣與查詢共用受控刷新，預算不足可略過背景取樣；訓練 collector 不參與用戶查詢。
  • 討論中：主查詢的輸入／輸出語意、Google Routes 與 Places 的責任分工。
  • 待定：正式 API、背景取樣間隔與歷史保留／歸檔、最低刷新間隔、Redis 快取粒度與 TTL、前景等待與輪詢上限、請求預算與模型介面。
資料：共同欄位方向已定，映射待驗證

來源與統一化

  • 已定：新北市路邊／路外來源各由 adapter 轉成共同位置、來源對應及動態觀測欄位；未來新增政府或業者來源沿用此契約。訓練 collector 與主系統即時查詢分離。
  • 待驗：格位狀態碼與汽車適用性、來源 ID／座標、缺值與覆蓋率、來源觀測時間、路外有效剩餘位欄位。
  • 待驗：新莊邊界資料是否覆蓋完整，如何標示未收錄的鄰區。
預測：資料盤點暫緩，模型未開始

抵達時有位機率

  • 路邊：目的地 300 公尺內至少一個適用汽車格位可停的機率；訓練標籤須對齊實際 300 公尺圓。
  • 路外：範圍內各停車場抵達時仍有汽車位的機率。
  • 待處理：collector 匯出不完整；恢復後才驗證標籤、樣本品質、時間與街區切分、基準及模型部署。資料不足時不編造機率。
服務整合：雲端專案與 API 已開通，未介接

Google 與外部地圖

  • 已定：Google Maps 用於地圖、Places (New) 用於搜尋、Routes 的交通感知 ETA 直接作預測時刻；外部地圖負責導航。Sponsor 回報停車專案 Taiwan Parking Forecast（ID taiwan-parking-forecast）已建立，三項 API 已啟用、帳單連結有效，預算通知已設定。
  • 帳單規劃由 Sponsor 自行管理，本階段跳過；網頁／後端金鑰限制及配額在正式介接前仍須核對。主系統尚未呼叫服務。
部署／驗收：方向已定，未實作

Docker 與品質證據

  • 已定：Docker 可部署到其他伺服器是必要交付；面試仍可本機展示，兩類預測都列入 20 天目標。
  • 待做：容器建置與乾淨主機啟動、MySQL 持久化／備份驗證、遠端 HTTPS 與金鑰設定、並發刷新測試、資料年齡及 API 用量量測、兩類模型與基準比較。
  • 待確認：實際主機、網域與遠端上線是否納入 20 天時程。

下一步最重要的三個決策

  1. 定主系統查詢輸入、ETA／停車結果分層及前後端 API 契約。
  2. 確認主系統即時來源刷新控制與上游請求量測方式。
  3. 確認遠端 Docker 部署目標；訓練資料盤點待 collector 問題釐清後恢復。
